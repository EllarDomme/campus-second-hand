# 07 · 易错点与踩坑清单

> 这份清单来自**实际写代码时真实犯过的错误**，不是通用注意事项。
> 按「错误模式」归类，因为同一个模式会反复出现——按时间罗列没有用，记住模式才有用。
>
> **用法**：每次写完一个方法，用最后一节的「10 秒自查清单」过一遍。

---

## 一、高频模式（犯过 3 次以上）

### 模式 1：null 安全 —— 「先用后判空」🔴 最高频

**犯错记录**：

| 场景 | 错误写法 | 后果 |
|---|---|---|
| 议价列表（S3-4a）| `queryDTO.getView().equals("buyer")` | `view` 为 null 时 **NPE，接口 500** |
| 议价出价校验（S3-6a）| `getBuyerOffer().compareTo(...)` 写在判空**之前** | 出价传 null 时 **NPE** |
| 超时任务（S3-5a）| `if(expiredList.isEmpty() \|\| expiredList == null)` | 真的为 null 时 **NPE**（顺序反了）|
| 详情方法（S3-4a）| 接口写 `Long id`、实现写 `long id` | 不一致；基本类型永远不可能是 null，丢掉了"判空"的机会 |

**规则**：

1. **先判空，再使用** —— 顺序不能反，判断条件也从左到右执行
2. **`常量.equals(变量)`，不要 `变量.equals(常量)`** —— 常量不可能是 null
3. **多个值比较时，把"你确定非空的"放前面调用 `.equals()`**
4. **id 一律用包装类**（`Long` 而不是 `long`），给"判空"留余地

**为什么重要**：NPE 是最常见的线上事故来源；而且这类错误**测试正常路径时完全不暴露**。

---

### 模式 2：守卫判断写反 / 兜底分支缺失 🟠

**犯错记录**：

| 场景 | 错误写法 | 后果 |
|---|---|---|
| 超时关单（S3-5a）| `if (STATUS==待确认) return;` | 把**正要处理**的订单全部跳过了，定时任务形同虚设 |
| 超时关单（S3-5a）| `if (expireTime.isBefore(now)) return;` | 同上，"已过期"正是要处理的 |
| 议价列表（S3-6a）| `if(view=="seller"){...} else if(view=="buyer"){...}` | 参数异常时**两个分支都不进** → 过滤条件为空 → **返回全平台数据（数据泄露）** |
| 订单列表（S3-4a）| 默认值落到"我卖出的" | 不传参数时用户看到空列表，以为"我的订单没了" |

**规则**：

1. **`return`/`if` 的条件应该写「什么情况下不该做这件事」**，而不是「什么情况下该做」
   —— 写后者容易把条件写反
2. **凡"根据参数决定查哪一边"的过滤，必须有一个兜底分支**（用 `else`，不要用 `else if`）
   —— 过滤条件一旦整个消失，SQL 就从"查我的"变成"查全部"，**不报错，直接泄露**
3. **默认值要主动选择**：问自己"参数没传时，返回什么最合理、最安全"

**为什么重要**：这类 bug 有两个可怕的特点——**不报错**、**正常路径测不出来**。

---

### 模式 3：该抛异常的地方写了 `return`（事务不回滚）

**犯错记录**：

| 场景 | 错误写法 | 后果 |
|---|---|---|
| 买家确认收货（S3-4c）| 商品状态更新**没判断影响行数** | 商品状态没改成功，订单却已完成 → 数据不一致 |
| 超时关单（S3-5a）| `if (back == 0) return;` | 订单已取消+已退款**已提交**，商品却还锁着 → 数据烂掉 |

**规则**：

1. **用了条件更新（`where ... and status = 旧值`），就必须判断影响行数** —— 不判断的话这个条件更新等于白写
2. **在 `@Transactional` 方法里，失败要 `throw`，不要 `return`**
   - `throw` → 整个事务回滚，数据保持一致
   - `return` → 事务正常提交，**留下半成品数据**
3. 一句话：**"立刻失败"永远好过"静默留下错数据"**

### 模式 4：常量与魔法数字

**犯错记录**：

| 场景 | 错误写法 | 问题 |
|---|---|---|
| 卖家拒单（S3-4b）| `.status(3)` `.payStatus(2)` `.payType(2)` | 同一个文件里 `confirm` 用了常量、`reject` 用裸数字，**风格不一致**；3 是啥？ |
| 议价冷却期（S3-6a）| 用了 `EXPIRE_HOURS`（议价有效期）| 两个常量碰巧都是 24，语义却完全不同，将来改一个会影响另一个 |
| 议价下限（S3-6a）| `divide(new BigDecimal("2"), ...)` | 把"不低于 50%"这条**业务规则**硬编码成 `÷2`；改成 60% 时这段代码不会跟着变 |

**规则**：

1. **数字出现在业务逻辑里，先问"它有没有名字"** —— 有名字就用常量
2. **同一个概念只能有一个出处**；两个语义不同的概念，即使数值相同也要用两个常量
3. 常量类的价值就是**把业务规则集中到一个地方**

### 模式 5：权限判断用「排除法」而不是「允许法」🔴 安全级

**犯错记录**：

| 场景 | 错误写法 | 后果 |
|---|---|---|
| 议价-接受报价（S3-6b）| `if (me.equals(buyerId)) throw "买家不能接受自己的出价";` | 只拦住了买家 → **跟这笔议价无关的第三人照样能通过**，替别人成交、锁掉别人的商品 |

**规则**：

```java
// ✅ 允许法（白名单）：只有"该做的人"能过
if (!me.equals(bargain.getSellerId())) {
    throw new BaseException("只有卖家可以接受这个报价");
}

// ❌ 排除法（黑名单）：只拦住"已知不该做的人"，其他人全放行
if (me.equals(bargain.getBuyerId())) {
    throw new BaseException("买家不能接受自己的出价");
}
```

**为什么**：你**永远列不全**"不该做的人"（陌生人、管理员、跑腿员、以后新增的角色……），
但你**总能准确说出**"该做的人是谁"。**白名单是封闭的，黑名单是开放的。**

**附带一条：fail-closed vs fail-open**

| 判断类型 | 出错（null/异常）时怎么选 | 例子 |
|---|---|---|
| "我能不能做这件事？" | **拒绝**（fail closed）| 议价过期校验：`expireTime` 为 null → 当作已过期 → 不放行 |
| "我要不要主动改掉/毁掉某样东西？" | **不动**（fail open）| 超时关单：`expireTime` 为 null → 不取消订单 |

两者都是"保守"的：**一个是不放行，一个是不动手，共同点是都不造成伤害。**

## 二、一次性但值得记住的坑（各犯过 1 次）

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | **`==` 比较包装类型** | `order.getPayStatus() == OrderConstant.PAY_PAID`（Integer）| 值在 -128~127 时因 Integer 缓存**恰好能跑**，超过就突然失效。**一律用 `.equals()`** |
| 2 | **`@PathVariable` 用在没有 `{id}` 的路径上** | `@PutMapping("/confirm")` + `@PathVariable Long id` → `MissingPathVariableException`，接口 500 | 路径里有 `{id}` 才能用 `@PathVariable`；否则用 `@RequestParam` |
| 3 | **`select *` + join** | 两张表都有 `id`/`status`/`create_time` → 列名撞车，**填进 VO 时只有一个能赢，不报错** | 一律逐列写明并起别名；别名必须等于 VO 属性名 |
| 4 | **Mapper 返回类型与 XML `resultType` 不一致** | `Page<TradeOrder>` vs 要装 `productTitle` 的 `TradeOrderVO` | 返回类型必须等于 `resultType`，且**必须装得下你 select 的所有列** |
| 5 | **Mapper 方法参数没写名字** | `Page<X> pageQuery(SomeDTO);` → 编译不过 | 参数必须有名字：`pageQuery(SomeDTO query)` |
| 6 | **SLF4J 占位符写错** | `log.warn("...{payno}...", payNo)` → 日志里原样打印 `{payno}`，值丢了 | 占位符是 `{}`，**日志里没有关键 ID 会让排错很痛苦** |
| 7 | **漏 `@Transactional`** | 拒单要改三张表却没加注解 | **多表写操作必须加**；但**不要加在循环/定时任务方法上**（否则整批绑一个事务） |
| 8 | **业务条件漏判** | 未支付的订单被标成"已退款" | 状态字段的变化要问"这个值在当前情况下成立吗"，不能无条件写 |
| 9 | **残留物没清** | 无用 import、变量名 `back` 却用于"标记已售罄" | 提交前扫一眼；**命名要跟着语义走** |

## 三、开工前 10 秒自查清单 ⭐

> 写完一个方法，从下往上过一遍：

```
□ 1. 用到的每个值，可能为 null 吗？→ 先判空再使用；常量放前面
□ 2. 这个 if 写的是"什么情况该走开"，还是"什么情况该干活"？
□ 3. 分支覆盖全了吗？参数异常/没传时会走到哪里？会不会两个都不进？
□ 4. 有用条件更新吗？→ 判断影响行数了吗？
□ 5. 该抛异常的地方，是不是写成了 return？（事务会不回滚！）
□ 6. 数字/字符串是硬编码，还是取自常量？这个常量语义对吗？
□ 7. 多张表写入 → 加 @Transactional 了吗？（但别加在循环上）
□ 8. 返回类型和 XML 的 resultType 对得上吗？能装下 select 的所有列吗？
□ 9. 日志里的关键 ID 打出来了吗？占位符是 {} 吗？
□ 10. 无用 import、语义不符的变量名，清了吗？
□ 11. 权限判断用的是「允许法」（只有该做的人能过），还是「排除法」（只拦住了已知不该做的人）？
□ 12. 出错时该 fail-closed（拒绝）还是 fail-open（不动手）？
```

## 四、概念确认：哪些类需要 IOC 注解

> 判断标准一句话：**这个类的实例，是"我自己 `new` 出来的"，还是"希望 Spring 给我一个"？**

| 类型 | 需要注解吗 | 原因 |
|---|---|---|
| Controller | ✅ `@RestController` | Spring MVC 要识别成接口 |
| Service 实现类 | ✅ `@Service` | 要注入到 Controller |
| Mapper | ✅ `@Mapper` | MyBatis 扫描后生成代理 |
| 工具/组件 | ✅ `@Component` | 要注入到别处 |
| **entity / VO / DTO** | ❌ **绝对不能加** | 见下 |
| Service **接口** | ❌ 不需要 | 接口由实现类注册，注入时按类型匹配 |

### 为什么实体类不能是 Bean ⚠️

**Spring 的 Bean 默认是「单例」：整个应用只有一份实例，所有请求共享同一个对象。**

如果给实体类加了 `@Component`：

```
A用户抢购 → record.setUserId(1)
B用户抢购 → record.setUserId(2)      ← 两人操作的是同一个对象
A用户读出来 → userId = 2            ← 数据串号
```

实体类天生"装状态"，**有状态的类不能做单例**。我们创建实体的方式是 `new` / `builder()`，
每个请求一份、彼此隔离，天然线程安全 ✓

> **同源陷阱**：Controller / Service 都是单例，所以**里面不能写"用来存请求数据的成员变量"**
> （只能写注入进来的依赖）。例如在 Controller 里写 `private Long currentUserId;` 然后赋值 —— 所有用户会互相覆盖。

### 怎么验证 IOC 装配是否正确

**看服务能不能启动。** 少一个 Bean 或注解写错，启动会直接失败并报：

```
No qualifying bean of type 'com.sky.service.XXXService' available
```

所以"启动成功"本身就是装配正确的证明 —— 启动失败时第一件事就是找这类报错。

## 五、流程纪律（这几条能省掉大量"白忙活"）

> 前面四节是"代码写错"，这一节是"流程走错"——**更冤，因为技术上是会的**。

| # | 纪律 | 踩坑记录 |
|---|---|---|
| 1 | **改完源码 → 先编译 → 再重启 → 再测试** | 有一次给 `counter` 加了过期校验却忘了编译，服务器跑的还是旧 class，测试报"校验没生效"，白查了半天。**自查办法：class 文件时间必须比源码新** |
| 2 | 测试脚本里的**中文要 URL 转义** | Python `urllib` 不接受 URL 里的非 ASCII 字符，直接拼中文地点会报 `'ascii' codec can't encode`。用 `urllib.parse.quote(...)` |
| 3 | **测试数据必须可重复** | 每轮回归都会新造订单，重置脚本若不清理，跑十几轮后表里堆一堆；断言"最新一条"虽然还能过，但人工核对时完全看不懂 |
| 4 | 构造测试数据要**符合业务约束** | 曾把两条议价都挂在同一件商品上 → 第一条成交后商品被锁，第二条必然失败。**一件商品只能卖一次**，测试数据不能自相矛盾 |
| 5 | 回归脚本**别把失败详情过滤掉** | runner 的过滤器只放行 ✅/❌ 行，把"期望包含/实际返回"滤掉了，失败时看不到原因，只能单独再跑一遍 |

**一句话**：**代码问题靠自查清单，流程问题靠固定动作**（编译→重启→测试，一步都别跳）。

## 六、这些坑的面试价值 🎯

**能讲出"自己踩过的坑 + 怎么防复发"，比背八股有用得多。** 几个现成的说法：

| 面试官可能问 | 你可以答 |
|---|---|
| 你遇到过并发问题吗？ | "商品只有一件，两个人同时下单。我用**条件更新 + 判断影响行数**，靠数据库行锁保证只有一个人成功。测试时用 10 个线程验证，恰好 1 个成功。" |
| 讲一个你修过的 bug | "列表接口用 `else if` 判断视角，参数异常时过滤条件为空，**返回了全平台数据**。我加了兜底分支，并补了两条回归用例专门盯这个。" |
| 用过事务吗？ | "拒单要改订单、流水、商品三张表，我加了 `@Transactional`。还特意做了破坏性测试：故意让商品回退失败，验证订单状态确实回滚了。" |
| 怎么保证代码质量？ | "我维护了一套回归测试，49 项断言一键跑完；`BigDecimal` 比较、判空顺序这些易错点都写进了自查清单。" |
| `BigDecimal` 能用 `equals` 比大小吗？ | "不能。`equals` 比的是值和精度，`25.0` 和 `25.00` 不相等；要用 `compareTo`。我的议价出价校验就用了 `compareTo`。" |
