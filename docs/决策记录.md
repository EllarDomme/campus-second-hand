## 〇、已拍板的决定（2026-10-10，做到阶段 3 时按这个执行）

### 决定：做「模拟支付 + 担保交易」（第 ② 档）

**背景**：原计划是"平台不介入资金、纯线下面交"。后经讨论改为**要做支付**，理由：

1. **数据可信**（决定性理由）：钱不过平台的手，平台就只能"记录"、不能"保证"。
   订单写 35 元、线下实际给 30 元 → 平台数据失真 → 纠纷举证和信用分计算都失去依据。
   **支付是唯一能强制「钱和订单金额一致」的机制。**
2. **用户体验**：学生本来就在线转账（只是在微信/支付宝里转，平台拿不到数据）。

**档次选择：第 ② 档（模拟支付通道）**，因为：

| 档次 | 能否做 |
|---|---|
| ① 真实资金通道 | ❌ 需要企业资质 + 商户号；平台代收代付涉及资金池合规，学生项目做不到 |
| **② 模拟支付 + 担保交易** | ✅ **选这个**：完整实现支付链路逻辑，资金是模拟的 |
| ③ 只设计规则不接通道 | ✅ 能做但没有技术含量 |

**流程选定：方案 A（下单即支付）**，理由：

- 与闲鱼/转转一致，用户习惯、面试官熟悉
- **能最大化复用苍穹外卖原有代码**：原有的"未支付超时自动取消"定时任务几乎原样可用
- 状态环节更少（4 步 vs 方案 B 的 5 步）
- 方案 B 有一个致命问题：卖家确认后买家不付钱 → 商品被锁、卖家白等，还得再加一套支付超时
- 方案 A 能挡住"随便点一下就把商品占住"的行为（校园二手平台很容易被玩坏的点）

**完整流程**：

```
下单 → 【待支付】--支付成功(钱进平台托管)--> 【待确认】卖家确认
     → 【待交易】面交验货 → 买家确认收货 → 【已完成】平台放款给卖家 → 双方互评
     └ 15 分钟未支付 → 超时取消，商品重新上架
     任意一方在交易前取消 → 模拟退款 → 商品重新上架
```

**超时时长**：普通订单 **15 分钟**（沿用原工程）；捡漏抢购订单 **10 分钟**（与需求里的抢购窗口一致）。

**需实现的 6 件事（阶段 3）**：

1. 订单加 `pay_status`（0未支付 1已支付 2已退款）、`pay_time`、`pay_no`（**唯一索引**）
2. "发起支付"接口 + "支付结果通知"接口（模拟回调）
3. ⭐ **回调幂等**：同一笔支付通知重复到达不能重复处理（靠 `pay_no` 唯一约束兜底）
4. **担保逻辑**：付款进托管 → 确认收货后放款
5. ⭐ **超时未支付自动关单**（可复用原工程定时任务，只改状态条件）
6. 取消订单 → 模拟退款记录

**表结构变更**：订单表加 3 个字段 + 建议新增 `payment_record` 支付流水表（用于对账，也是面试讲点）。

**面试口径**：

> "支付是**模拟通道**——微信支付需要企业资质，学生项目拿不到。但完整链路我实现了：
> 下单创建支付单 → 模拟支付成功 → 回调通知 → **回调幂等校验** → 订单状态流转 →
> 资金进托管 → 确认收货后放款。重点在回调幂等：支付平台的通知可能重复送达，
> 我用支付流水号做唯一约束，重复通知直接返回成功但不会重复处理。
> 接真实通道只需把模拟那一步换成 SDK 调用，其余逻辑不用改。"

**⚠️ 代价（要认）**：要改数据库表、改需求文档、阶段 3 工作量增加、原"删除支付代码"的计划要改为"保留骨架 + 重写为模拟通道"。
