## 一、总体策略

**保留技术骨架，替换业务外壳。** 下面这些是"骨架"，一行都不用动：

| 类别 | 具体内容 | 为什么不动 |
|---|---|---|
| 统一响应 | `Result` / `PageResult` | 前端已适配 |
| 上下文 | `BaseContext`（ThreadLocal 存当前用户 id） | 登录态传递的标准做法 |
| 异常体系 | `BaseException` + 12 个业务异常 + `GlobalExceptionHandler` | 全局异常处理完整 |
| JWT | `JwtUtil` / `JwtProperties` / 两个拦截器 | 双端（管理员/用户）令牌分离，正是我们要的 |
| 公共字段填充 | `@AutoFill` + `AutoFillAspect` | 自动填 create/update time 和 user |
| 对象映射 | `JacksonObjectMapper`（时间格式） | 前端时间格式依赖 |
| 配置 | `RedisConfiguration` / `OssConfiguration` / `WebSocketConfiguration` | 中间件与实时通信基建 |
| 拦截器注册 | `WebMvcConfiguration` | 只改放行路径 |

## 二、现有代码处置清单

### 2.1 直接删除（业务形态不匹配）

| 删除对象 | 原用途 | 为什么删 |
|---|---|---|
| `Setmeal` / `SetmealDish` / `SetmealDTO` / `SetmealVO` / `SetmealPageQueryDTO` / `SetmealMapper` / `SetmealService(Impl)` / `SetmealController`(admin+user) / `SetmealOverViewVO` / `SetmealPageVO` | 套餐（菜品组合） | 二手商品没有"套餐"概念，一件就是一件 |
| `ShoppingCart` 全套（entity/DTO/Mapper/XML/Service/Impl/Controller） | 购物车 | 二手上架商品每件唯一，直接下单，不需要购物车 |

| `DishFlavor` 全套（entity/DTO/Mapper/XML） | 菜品口味 | 二手商品没有"口味/规格选项" |
| `AddressBook` 全套（entity/DTO/Mapper/XML/Service/Impl/Controller） | 收货地址簿 | 改为"交易地点"，直接落在订单上（见 §4 决策 3） |
| `WeChatPayUtil` + `PayNotifyController` + 支付相关 DTO/VO | 微信支付 | 平台不做线上支付，线下当面结算（需求明确：避开资金流转） |
| `ReportService` / `WorkspaceService` 及其 Controller、相关 VO | 营业额/销量统计报表 | 阶段 4 再按二手平台口径重建（订单量、成交额、热门分类、捡漏参与数） |

> ⚠️ 删除时注意：`OrderServiceImpl` / `DishServiceImpl` 里对上述类的引用要一起清掉，否则编译不过。
> 建议**一批一批删**（先删套餐，编译一次；再删购物车，再编译），不要一次删完再编译——报错会淹没你。

### 2.2 改名改造（业务语义替换）

| 现有 | 改造为 | 关键字段变化 |
|---|---|---|
| `Dish` → `Product` | 菜品 → 闲置商品 | `name`→`title` `image`→`images`(JSON 多图) `status` int→tinyint 新增 `is_flash_sale` / `flash_start_time` |
| `Orders` → `TradeOrder` | 订单 → 交易订单 | 删 `address_book_id`/`pay_method`/`pay_status`/`delivery_status`/`pack_amount`/`tableware_*`/`consignee`/`rejection_reason`；新增 `order_no`/`seller_id`/`real_price`/`deal_type`/`order_source`/`expire_time`/`finish_time` |
| `Category` → 保留 | 分类 | `name`→`category_name`；删 `type`/`sort`/`status`/`create_user`/`update_user`（二手平台分类只有一种，也无需排序） |
| `User` → 保留改造 | 用户 | `name`→`nickname`；删 `sex`/`id_number`(**身份证敏感信息不存**)；`avatar` 保留；新增 `real_name`/`student_no`/`credit_score`/`role`/`status` |
| `OrderTask` → 保留改造 | 超时扫单 | 捡漏预订单 10 分钟、普通订单 30 分钟，两套超时（对应 `order_source`） |
| `WebSocketServer` → 保留改造 | 原为商家端来单提醒 | 改为**用户间私信**（一对一）+ 系统通知（对应 `message` 表） |

### 2.3 新增（阶段 2 / 3 分两批）

| 层 | 阶段 2 新增 | 阶段 3 新增 |
|---|---|---|
| entity | `Product` `Favorite` | `Bargain` `TradeOrder` `DeliveryOrder` `Review` `Complaint` `FlashSaleRecord` `Message` |
| mapper (+xml) | `ProductMapper` `FavoriteMapper` | 其余 6 套 |
| service (+impl) | `ProductService` `FavoriteService` `CategoryService`(改) | `BargainService` `TradeOrderService` `DeliveryOrderService` `ReviewService` `ComplaintService` `FlashSaleService` `MessageService` |
| controller | `user/ProductController` `user/FavoriteController` `admin/ProductController`(审核) | `user/BargainController` `user/TradeOrderController` `user/DeliveryOrderController` `user/ReviewController` `user/ComplaintController` `user/FlashSaleController` `user/MessageController` + 对应 admin |
| constant | `RoleConstant` `ProductStatusConstant` | `BargainStatusConstant` `OrderStatusConstant` `OrderSourceConstant` `DealTypeConstant` `DeliveryStatusConstant` `ComplaintStatusConstant` |

> 常量类是你的"状态枚举单一来源"：数据库存 0/1/2，代码里禁止裸写数字。面试问"状态怎么管理的"，这就是答案。
> 建议做法：一个状态一个常量类，或者用一个 `XxxStatus` 枚举 + `tinyint` 值的集中定义。

## 三、阶段 2 里程碑与验收（写代码的节奏）

> 每个里程碑都必须能独立跑通、能验收，再进行下一个。这就是你自己那份笔记里的"小增量开发"。

### M2.1 新库 + 实体打通

### M2.2 openid 登录（替换账号密码）
- `POST /user/user/login`：入参 `{code}` → 调微信接口换 openid → 查/建用户 → 签发用户 JWT
- 本地无微信环境：用 `testLogin`（已有调试开关）直接按 openid 登录取 token
- **验收**：`/user/user/login` 返回 token；带 token 访问需登录接口返回 200，不带 token 返回 401

### M2.3 分类
- 管理员：新增/修改/删除/分页；用户端：`GET /user/category/list`
- **验收**：新增分类后用户端能查到；删除有商品关联的分类要报业务异常（不是数据库报错）

### M2.4 商品（本阶段重头）
- 发布：多图 JSON 数组、分类校验、敏感词过滤
- 列表：分页 + 按分类过滤 + 价格/时间排序
- 详情、上下架（卖家本人校验：不能改别人的商品）
- **验收**：发布→列表能查到→详情正确→下架后列表不再出现

### M2.5 收藏
- 收藏/取消/我的收藏列表；商品售罄时列表标记【已售罄】且不可下单

## 四、需要你拍板的设计问题

| # | 问题 | 背景 | 影响 |
|---|---|---|---|
| 1 | **管理员认证走哪张表？** | 苍穹外卖用独立 `employee` 表（账号密码）；但 docx 设计里 `user.role` 有 `2=管理员` | 决定要不要保留 `employee` 表和 `JwtTokenAdminInterceptor` 那套；我倾向**保留 employee**（管理员是平台运营，不是学生，混进 user 表会让 credit_score/student_no 这些字段对管理员无意义） |
| 2 | 管理员端接口前缀 | 现在是 `/admin/**` 和 `/user/**` 两套拦截器 | 建议沿用，RBAC 校验放在 `/admin/**` 拦截器里做 |
| 3 | **交易地点存哪** | 阶段 1 缺口 3；`trade_order` 需要一个地点字段 | 建议 `trade_order.pickup_place varchar(255)`，自提时必填；跑腿单另有 `pick_address`/`receive_address`，两者语义不同不重复 |
| 4 | 敏感词过滤怎么做 | 需求要求商品发布 + 私信都过滤 | 建议先做**本地词库 + DFA/Trie 实现**（能讲清原理，不依赖外部服务）；面试常问"你怎么实现的" |

> 这 4 个和阶段 1 的 4 个缺口一起，构成你面试时"我做过设计决策"的素材。**先把结论写下来**，再动手。

## 五、面试口径（阶段 2 结束时你要能讲）

1. 为什么用 openid 而不是账号密码？（小程序无密码体系，openid 由微信侧保证唯一）
2. 为什么保留 `employee` 独立表？（角色边界清晰：平台运营 vs 学生用户）
3. 商品多图为什么用 JSON 字符串而不是子表？（一对少、无独立查询需求，避免多一次 join；代价是不能按图片维度查询）
4. 收藏为什么用联合唯一索引？（数据库层兜住并发重复插入，代码层再查一次是为了给用户友好提示）
5. 状态字段为什么用 tinyint + 常量类？（省空间、可索引、避免字符串拼写错误；常量类统一取值来源）
