# 一、分层架构（面试开场画这个）

```
┌──────────────────────────────────────────────────────────────────┐
│ 接入层                                                            │
│                                                                  │
│   用户端 56 个接口                管理端 36 个接口                 │
│   /user/**                       /admin/**                      │
│   请求头: authentication           请求头: token                  │
│                                                                  │
│   WebSocket:  /ws/{sid}?token=xxx   ← 不经过 Spring 拦截器！      │
└──────────────────────────────┬───────────────────────────────────┘
                               │
              ┌────────────────▼────────────────┐
              │ 拦截器（MVC）                     │
              │  · JWT 解析 → BaseContext        │
              │  · 封禁检查（Redis 缓存 5 分钟）   │
              └────────────────┬────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────────┐
│ 业务层 Service（11 个模块）                                        │
│                                                                  │
│  商品   订单   支付   议价   捡漏   私信   跑腿   评价   信用分     │
│                                    投诉    数据看板                │
└──────────────────────────────┬───────────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────────┐
│ 数据层                                                            │
│                                                                  │
│  MyBatis Mapper ──▶ MySQL（15 张表）                              │
│                                                                  │
│  Redis：                                                          │
│   · 捡漏库存（Lua 原子扣减）      ← 流量闸门                       │
│   · 封禁状态缓存（TTL 5 分钟）    ← 让封禁"很快"生效               │
│   · 商品详情缓存                                                 │
│                                                                  │
│  定时任务（每分钟）：订单超时关单 / 议价过期                       │
```

**画这张图时要说的一句话**

> "关键在两点：一是**两个端有两套 token**；二是 **WebSocket 不在拦截器覆盖范围内**，所以它的鉴权是自己做的。"

# 二、15 张表的关系（按业务域分组，别平铺）

> 白板上**不要**画 15 个方框 —— 面试官记不住。分组画，只画连线，不画字段。

```
【主体】
   employee                          user
                                        │
【商品】                                 │
   category ──< product >─── favorite ──┘
                  │  │  │
                  │  │  └──< flash_sale_record     抢购记录（uk: product+user）
                  │  └─────< bargain               议价单
                  │
【交易】           │
   trade_order >──┴──┬──< payment_record    支付/退款流水（uk: pay_no）
       │             ├──< delivery_order    跑腿单（uk: trade_order 一笔一单）
       │             ├──< review             评价（uk: order+from 一单一评）
       │             └──< complaint          投诉工单
       │
【沟通】             
   conversation >────< message              会话按 (商品+买家+卖家) 三元组唯一
   
【信用】
   credit_log                               信用分流水（唯一数据源，总分靠它算）
```

**图例**：`<` 表示"一对多"，`>` 表示"被引用"

**画这张图时要说的一句话**

> "15 张表里，**交易域是核心**，其余都围绕它：支付、跑腿、评价、投诉、信用分，都是挂在一笔交易上的副产物。"
> "有两张表比较特别：`conversation` 是按'商品+买家+卖家'三元组做唯一的，`credit_log` 是**信用分的唯一数据源** —— 总分不直接改，靠流水累加。"

# 三、核心链路：限时捡漏抢购（**这是你最强的一张图**）

```
   用户 (几十个同时点"抢")
        │
        ▼
┌───────────────────────────────────────────┐
│ ① Redis 预扣（Lua 脚本，原子）              │
│                                           │
│   local stock = GET  stock:product:{id}   │
│   if stock == false  then return -1 end   │ ← key 还没建，需惰性初始化
│   if tonumber(stock) > 0 then             │
│       DECR stock:product:{id}             │
│       return 1                            │
│   end                                     │
│   return 0                                │ ← 没货了
│                                           │
│   作用：把几十个请求挡到只剩 1 个            │
│   惰性初始化：第一次有人抢时用 SETNX 建 key │
│   （不用在"商品上架/下架"时同步 Redis，      │
│     少一处状态就少一处不一致）              │
└───────────────────┬───────────────────────┘
                    │ 只有扣成功的才继续
                    ▼
┌───────────────────────────────────────────┐
│ ② 数据库条件更新（最终裁判）                 │
│                                           │
│   UPDATE product                          │
│      SET status = 1                       │
│    WHERE id = ? AND status = 0            │
│                                           │
│   影响行数 = 0 → 抛"已被抢走"               │
└───────────────────┬───────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────┐
│ ③ 插入抢购记录（唯一索引兜底）               │
│                                           │
│   INSERT INTO flash_sale_record           │
│     (product_id, user_id, ...)            │
│   -- uk_product_user(product_id, user_id) │
│   -- 撞键 → DuplicateKeyException → 幂等   │
└───────────────────┬───────────────────────┘
                    │
                    ▼
              生成订单 + 返回成功
                    │
        ┌───────────┴───────────┐
        │ ②或③ 失败              │
        ▼                       ▼
   ┌─────────────────┐     直接抛异常给用户
   │ 补偿：Redis 库存 +1│
   │ （失败则打 ERROR   │
   │   日志，人工核对）  │
   └─────────────────┘
```

**这张图要配的那句话（最重要）**

> "三层里只有第二层是'必须对'的。第一层是挡箭牌，挡错了数据库会兜住；
> 第三层是防重复，业务层挡不住时它兜底。"
>
> "补偿的方向我特意选成'**宁可 Redis 偏高**' —— 因为偏高会被数据库拦住，只是白跑一趟；
> 偏低会让商品永远抢不到。"

# 四、5 条状态机

## ① 交易订单

```
                    ┌──────────── 买家取消 / 卖家拒绝 ───────────┐
                    │                                          ▼
   ┌──────────┐   卖家确认   ┌──────────┐  买家确认收货  ┌──────────┐
   │ 0 待确认  │ ──────────▶ │ 1 待交易  │ ───────────▶ │ 2 已完成  │
   └────┬─────┘              └────┬─────┘               └──────────┘
        │                         │
        │ 超时(定时任务)            │ 买家取消
        ▼                         ▼
   ┌────────────┐            ┌──────────┐
   │ 4 超时取消  │            │ 3 已取消  │
   │（扣买家 -5）│            └──────────┘
   └────────────┘
```

> **为什么把"已取消"和"超时取消"分开**：运营要看"多少单是人主动放弃的、多少是超时流失的"。
> 而且**只有超时才扣信用分** —— 主动取消是正常行为，不该罚。

## ② 跑腿单

```
   ┌────────────┐  跑腿员抢单  ┌────────────┐        ┌────────────┐        ┌────────────┐
   │ 0 待接单    │ ──────────▶ │ 1 已接单    │ ─────▶ │ 2 取货中    │ ─────▶ │ 3 已送达    │
   └─────┬──────┘  (条件更新)   └─────┬──────┘        └─────┬──────┘        └────────────┘
         │                            │                     │
         └────────────────────────────┴─────────────────────┘
                    买卖双方可取消 / 管理员可强制取消
                              ▼
                        ┌────────────┐
                        │ 4 已取消    │
                        └────────────┘
```

> **已送达(3) 和 已取消(4) 都是终态** —— 管理员的"强制取消"必须同时拦住这两个。
> 我在这里踩过坑：只拦了"已送达"，漏了"已取消"，结果重复取消会**报成功但什么都不发生**。

## ③ 议价

```
   ┌────────────┐  卖家接受   ┌────────────┐
   │ 0 待回应    │ ─────────▶ │ 1 已接受    │ ──▶ 生成订单
   └─────┬──────┘             └────────────┘
         │
         ├── 卖家拒绝 ──▶ ┌────────────┐
         │                │ 2 已拒绝    │（24 小时内不能再议同一商品）
         │                └────────────┘
         │
         └── 超时 ──────▶ ┌────────────┐
                          │ 3 已过期    │（不扣信用分）
                          └────────────┘
```

## ④ 投诉工单

```
   ┌────────────┐  管理员"抢处理权"(条件更新)   ┌────────────┐
   │ 0 待处理    │ ──────────────────────────▶ │ 2 已完结    │
   └────────────┘                              └────────────┘
                                                     │
                                    处理结果：1 成立 → 被投诉人 -10 分
                                              2 不成立 → 不扣分
```

> **为什么用"抢处理权"而不是"先查再改"**：两个管理员同时处理同一张工单，
> 先查再改会让两个人**都看到"待处理"、都执行** → 重复扣分 ✗
> 条件更新让只有一个能推进，另一个拿到 0 行 → 提示"已被处理" ✓

## ⑤ 信用分（不是状态机，是"数值 + 额度"）

```
   credit_score:  0 ─────────────────────────▶ 100+（无上限）
                   ▲（下限 0，扣到底也不会变负）

   分值规则：
    交易完成    +2
    收到好评    +1（4~5 星）
    收到差评    -2（1~2 星）
    超时爽约    -5
    投诉成立   -10
    管理员调整  ±1 ~ ±20（需填原因）

   每日加分上限 10
     · 只限制【加分】—— 如果连扣分也限，等于保护恶意用户
     · 【补偿性加分豁免】—— 撤销差评不是刷分，不该被上限吞掉
```

# 五、⭐ 白板作画顺序（练这个，别练上面的图）

**总原则：4 步，每步 1 分钟以内，画完一个再画下一个。**
**永远不要一上来就画 15 张表** —— 面试官会失去耐心。

## 第 1 步：画一条业务主线（30 秒）

```
发布商品 → 议价 → 下单 → 支付 → 交付(自提/跑腿) → 评价 → 信用分
```

**边画边说**
> "业务主线是这样：学生发布二手商品，买家可以私聊议价、也可以直接下单；
> 支付走担保交易；交付要么线下自提，要么叫跑腿帮送；成交后互相评价，形成信用分。"

## 第 2 步：圈出"和外卖最不一样的地方"（1 分钟）

```
                     ┌──────────────────────┐
                     │ 商品只有一件！         │
                     │  → 商品状态就是并发焦点 │
                     └──────────────────────┘
```

**边画边说**
> "外卖项目里一份菜可以无限卖，所以不存在超卖；二手商品只有一件，这就带来了一串问题：
> 超卖、重复支付、抢购、抢单。**我的主要工作量都在这些地方。**"

## 第 3 步：画抢购链路（1 分钟，**这是你最想让他看到的一张**）

```
   几十个请求
       │
       ▼
   Redis 预扣（Lua）   ← 挡箭牌
       │
       ▼
   DB 条件更新         ← 最终裁判
       │
       ▼
   唯一索引            ← 兜底
       │
       ▼
   补偿（方向：宁可 Redis 偏高）
```

**边画边说**
> "三层防御。第一层挡流量，第二层是唯一必须正确的，第三层防重复。
> 补偿失败的时候要问'往哪个方向错是安全的'——结论是宁可 Redis 偏高。"

## 第 4 步：画一条状态机（1 分钟，挑订单或跑腿）

```
  0 待确认 ──▶ 1 待交易 ──▶ 2 已完成
     │              │
     ▼              ▼
  4 超时取消      3 已取消
```

**边画边说**
> "每个推进都是 `update ... where id = ? and status = 旧值`，靠影响行数判断成败。
> 这样不用在 Java 里写一堆 if，也不会出现两个人同时推进。"

# 六、画图时的 5 个禁忌

| ❌ 别做 | 理由 |
|---|---|
| 一上来画 15 张表 | 面试官记不住，还会觉得你抓不住重点 |
| 画字段（id/name/create_time）| 白板上没人看得清，浪费时间 |
| 图很漂亮但一句话不说 | **边画边讲**，沉默的画图 = 冷场 |
| 讲"我用了 Spring Boot / MyBatis" | 框架是默认项，不是亮点 |
| 被问"你这个图画得挺细"就继续加细节 | 该收就收，把时间留给讲**为什么** |
