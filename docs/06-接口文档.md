## 一、全局约定

| 项 | 说明 |
|---|---|
| 服务地址 | `http://localhost:8080` |
| 在线接口文档 | `GET /doc.html` |
| 统一响应格式 | `{"code": 1, "msg": null, "data": ...}`；**code=1 成功，code=0 业务失败**（失败原因在 msg） |
| 时间格式 | `yyyy-MM-dd HH:mm:ss` |
| 分页请求参数 | `page`（从 1 开始）、`pageSize` |
| 分页响应结构 | `{"total": 总数, "records": [ ... ]}` |
| 金额 | `decimal`，保留两位小数 |
| 请求体格式 | `application/json; charset=utf-8`（**中文必须 UTF-8**，否则会存成 `????`） |

### 1.1 认证方式：JWT 双令牌（重要）

**管理端和用户端用的请求头名字不一样**，这是最容易踩的坑：

| 端 | 请求头名 | 怎么拿 |
|---|---|---|
| **管理端** | `token` | `POST /admin/employee/login` |
| **用户端** | `authentication` | `GET /user/user/testLogin?openid=xxx`（本地测试）<br>`POST /user/user/login`（微信 code 换 openid） |

### 1.2 HTTP 状态码的含义

| 状态码 | 含义 |
|---|---|
| 200 | 请求被处理了（**注意**：业务失败也是 200，要看 body 里的 `code`） |
| 401 | 未登录 / token 无效 / 请求头名字写错 |
| 404 | 接口不存在（可能是已被删除的老接口） |

> ⚠️ 业务失败时 HTTP 仍是 200、`code=0`。排查时**必须看服务日志里的异常栈**，body 里只会显示"未知错误"。

**发布商品请求体**（`ProductDTO`）：

```json
{
  "categoryId": 1,
  "title": "二手单片机开发板",
  "price": 35.50,
  "images": "[\"https://xxx/1.jpg\",\"https://xxx/2.jpg\"]",
```

| 字段 | 说明 |
|---|---|

> 请求体里**没有** `sellerId`、`auditStatus`、`status` —— 这些由后端控制，前端传了也会被忽略（防越权）。

### 2.8 用户端 · 交易订单（S3-2 下单 / S3-3 支付 / S3-4 流转）

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| POST | `/user/order/submit` | authentication | **买家下单**（详见下方） |
| POST | `/user/order/pay?orderNo=` | authentication | **发起支付**（模拟通道）→ 返回 `payNo` |
| GET | `/user/order/page` | authentication | **我的订单**：`view=buyer` 我买到的 / `view=seller` 我卖出的（不传默认 buyer）|
| GET | `/user/order/{id}` | authentication | **订单详情**（只有买卖双方能看，否则 `无权查看该订单`）|
| PUT | `/user/order/confirm/{id}` | authentication | **卖家确认**：待确认 → 待交易 |
| PUT | `/user/order/reject` | authentication | **卖家拒单**：body `{"id":5,"reason":"..."}`；已支付则退款，商品回退在售 |
| PUT | `/user/order/complete/{id}` | authentication | **买家确认收货**：待交易 → 已完成；商品转"已售罄"，并写一条放款流水 |
| PUT | `/user/order/cancel` | authentication | **取消订单**（交易前，买卖双方都能取消）：body `{"id":4,"reason":"..."}`；已支付则退款，商品回退在售 |

**支付回调（不需要登录，模拟支付平台调我们）**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/notify/paySuccess?payNo=` | **支付成功通知**：**幂等**，同一 `payNo` 重复调用不会重复处理，且每次都返回成功 |

**「拒单」和「取消」的请求体是同一个 DTO**（`TradeOrderCancelDTO`）——因为它俩形状完全一样（哪个订单 + 为什么），Service 里的核心逻辑也是同一份：

```json
{ "id": 5, "reason": "东西已经被同学买走了" }
```

| | 谁能发起 | 什么状态能做 |
|---|---|---|
| **拒单** `reject` | 只有**卖家** | 只有"待确认" |
| **取消** `cancel` | **买卖双方**都行 | "交易前"（待确认 或 待交易）|

**拒单 / 取消 会同时改三处数据（在一个事务里）**：

| 改哪 | 改成什么 |
|---|---|
| `trade_order` | `status=3`（已取消）+ `cancel_reason`；**已支付时**才把 `pay_status` 改成 2（已退款）|
| `payment_record` | 已支付时写一条退款流水（`pay_type=2`，流水号前缀 `REF`）|
| `product` | 从"交易中"回退到"在售"（**条件更新**，只回退状态确实是"交易中"的）|

**确认收货会改三处数据（也在一个事务里）**：

| 改哪 | 改成什么 |
|---|---|
| `trade_order` | `status=2`（已完成）+ `finish_time` |
| `product` | 从"交易中"变成"已售罄"（同样用条件更新 + 判影响行数）|
| `payment_record` | 写一条**放款**流水（`pay_type=3`，前缀 `SET`）——平台把托管的钱结算给卖家 |

**一笔订单的完整资金流（对账口径）**：

```
支付(PAY, +金额) → 平台托管 → 确认收货则放款(SET, −金额给卖家)
                            或 取消/拒单则退款(REF, −金额回买家)

每单的托管余额 = 支付 − 退款 − 放款，订单终结时必然为 0
```

> 现成的对账 SQL（可用来验证资金逻辑）：
> ```sql
> SELECT order_no,
>        SUM(CASE WHEN pay_type=1 THEN amount ELSE 0 END) AS 收到,
>        SUM(CASE WHEN pay_type=2 THEN amount ELSE 0 END) AS 退款,
>        SUM(CASE WHEN pay_type=3 THEN amount ELSE 0 END) AS 放款,
>        SUM(CASE WHEN pay_type=1 THEN amount ELSE -amount END) AS 托管余额
> FROM payment_record GROUP BY order_no;
> ```

**下单请求体**（`TradeOrderSubmitDTO`）：

```json
{
  "productId": 1,
  "dealType": 0,
  "pickupPlace": "3号宿舍楼下",
  "remark": "晚上7点后方便"
}
```

| 字段 | 说明 |
|---|---|
| `dealType` | 0自提 1跑腿（不传按自提） |
| `pickupPlace` | 交易地点（自提时填：宿舍区/教学楼/校门口） |

**成功响应**：

```json
{
  "code": 1,
  "data": {
    "orderId": 1,
    "orderNo": "202610110915435146",
    "realPrice": 45.00,
    "expireTime": "2026-10-11 09:30:44",
    "payStatus": 0
  }
}
```

**这个接口可能返回的业务失败（都是 code=0）**：

| msg | 原因 |
|---|---|
| 商品不存在 | productId 查不到 |
| 商品还未通过审核，暂时不能下单 | 商品 auditStatus ≠ 1 |
| 商品当前不可购买（可能已被别人拍下或已下架） | 商品 status ≠ 0（在售） |
| 不能购买自己发布的商品 | buyerId == sellerId |
| **手慢了，商品已被别人拍下** | 并发下条件更新影响 0 行（**这是真正的并发保护**） |

> 下单成功后：商品被锁成"交易中"（别人买不了了），订单状态 `status=0`（待确认）+ `payStatus=0`（未支付）
> —— 前端把这个组合显示成"**待支付**"。

### 2.9 用户端 · 议价（S3-6a 发起出价 / S3-6b 响应动作）

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| POST | `/user/bargain` | authentication | **买家发起议价** |
| GET | `/user/bargain/list` | authentication | **我的议价**：`view=buyer` 我发起的 / `view=seller` 别人对我商品出的价（不传默认 buyer）|
| PUT | `/user/bargain/accept/{id}` | authentication | **接受报价 → 成交并生成订单** |
| PUT | `/user/bargain/reject/{id}` | authentication | **拒绝报价** |
| PUT | `/user/bargain/counter` | authentication | **卖家还价**（body：`{"id":1,"counterOffer":20.00}`）|

**这三个响应接口买卖双方共用**，动作本身一样，区别只在"谁有权做"——由 Service 按当前状态判断：

| 议价状态 | 谁能 accept / reject | 谁能 counter |
|---|---|---|
| `1` 买家出价 | **卖家** | 卖家 |
| `2` 卖家还价 | **买家** | ❌ 单轮制，谁都不能再还 |
| `3/4/5` 终态 | ❌ 议价已结束 | ❌ 议价已结束 |

> ⚠️ **权限校验一律用「允许法」**（`if (!me.equals(sellerId)) throw`），
> **不要用「排除法」**（`if (me.equals(buyerId)) throw`）——
> 后者只拦住了已知不该做的人，跟这笔议价无关的**第三人照样能操作**。

**接受报价（成交）会同时做三件事（在一个事务里）**：

| 改哪 | 改成什么 |
|---|---|
| `product` | 在售 → **交易中**（锁商品，条件更新；已被别人买走则整笔失败）|
| `trade_order` | 新增订单：`order_source=2`（议价生成）、`real_price=` **最后一次报价**（有还价取还价）|
| `bargain` | `bargain_status=3`（已接受）+ 回填 `order_id` |

> 成交价取 **`bargain.currentOffer()`**（有卖家还价就是还价，否则是买家出价）。
> ⚠️ 议价成交生成的订单**交易地点为空**，买家之后用下面这个接口补充。

### 2.10 用户端 · 订单补充交易地点（S3-6b 配套）

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| PUT | `/user/order/pickup/{id}?pickupPlace=` | authentication | **买家补充/修改交易地点** |

**为什么需要它**：议价成交是"系统自动建单"，买家没有经过下单页面，**没机会填交易地点**，
必须能后补，否则双方不知道去哪里面交。

**校验**：只有**买家本人**能改 / 订单未结束（待确认或待交易）才能改 / 地点非空且 ≤255 字。

**发起议价请求体**：

```json
{ "productId": 3, "buyerOffer": 30.00 }
```

**议价状态**：`1 买家出价` `2 卖家还价` `3 已接受` `4 已拒绝` `5 已过期`

**业务校验**（不满足都返回 `code=0` + 中文原因）：

| 场景 | 提示 |
|---|---|
| 出价为 null | 出价不能为空 |
| 出价 ≤ 0 | 出价必须大于 0 |
| **出价 < 标价 × 50%** | 出价不能低于标价的 50% |
| 议价自己的商品 | 不能议价自己发布的商品 |
| 商品未过审 / 不在售 | 商品还未通过审核… / 商品当前不可议价（可能已被拍下或已下架）|
| 对该商品已有进行中的议价 | 你已经对这件商品出过价了，等对方回应吧 |
| 被拒绝后 24 小时内 | 对方刚拒绝过你的议价，24 小时后可以再试 |

> **出价下限**由 `BargainConstant.MIN_OFFER_RATE`（0.5）决定。
> `BigDecimal` 比较大小一律用 `compareTo`（`equals` 会因为 `25.0` 与 `25.00` 精度不同而误判）。

> ⚠️ **`view` 不传时必须兜底成 `buyer`**。这里曾经有过一个漏洞：用 `else if` 判断，
> 当 `view` 既不是 `buyer` 也不是 `seller`（比如 null）时**两个分支都不命中**，
> 过滤条件为空 → SQL 的 `WHERE` 整个消失 → **返回了全平台的议价记录**。
> **凡"根据参数决定查哪一边"的过滤，必须有一个兜底分支。**

## 三、已删除的接口（S3-5b 大扫除）

**这些接口的代码已经彻底删除了**（不是"失效"，是"不存在"），访问会返回 **HTTP 404**。
它们依赖的旧表（`orders` / `shopping_cart` / `address_book` / `order_detail`）在新库里本来就不存在。

| 模块 | 原路径 | 处理 | 替代方案 |
|---|---|---|---|
| 订单管理（旧） | `/admin/order/*`（8 个：conditionSearch、statistics、details、confirm、rejection、cancel、delivery、complete）| **删除**（旧的 `Orders` 模块整体移除）| 用户端 `/user/order/*`（`TradeOrder` 模块）；管理端的订单查询与统计留到阶段 4 |
| 地址簿 | `/user/addressBook/*`（7 个）| **删除** | 交易地点直接落在订单的 `trade_order.pickup_place` 字段上 |
| 购物车 | `/user/shoppingCart/*`（3 个）| **删除** | 二手商品每件唯一，直接下单，不需要购物车 |
| 订单明细 | （无对外接口）| **删除** | 一个订单只对应一件商品，用不上明细表 |
| 店铺营业状态 | `GET/PUT /admin/shop/{status}`、`GET /user/shop/status` | **仍保留**（待定）| 二手平台没有"店铺打烊"概念，倾向删除，但冒烟测试暂时用它做公开接口探活 |

**本次删除的规模**：37 个文件（旧订单模块 20 + 地址簿 6 + 购物车 7 + 订单明细 3 + 相关异常类），
外加 15 个已无引用的 `MessageConstant` 常量。
项目 Java 文件数从 **147 → 100**。

> 回归保障：`tools/smoke-test.ps1` 里有 4 条断言专门盯着"这些接口必须返回 404"，
> 万一以后有人误加回来，冒烟测试会立刻失败。

```powershell
$buyer = (Invoke-RestMethod "http://localhost:8080/user/user/testLogin?openid=test_openid_buyer_001").data.token
```

### 5.4 回归测试（一键）

```powershell
# 全部回归（推荐）：冒烟 18 项 + 订单模块 19 项 + 议价模块 12 项 = 49 项
powershell -ExecutionPolicy Bypass -File tools\run-regression.ps1

# 只跑冒烟（接口存活 / 已删除接口必须 404）
powershell -ExecutionPolicy Bypass -File tools\smoke-test.ps1

# 只跑某个模块（需先手动重置数据）
py -3 tools\order-flow-test.py        # 前置：source sql/test-reset.sql
py -3 tools\bargain-test.py           # 前置：source sql/test-reset-bargain.sql
```

| 脚本 | 覆盖 |
|---|---|
| `tools/smoke-test.ps1` | 公开接口存活、双端登录、分类/商品/收藏/议价/订单列表、**已删除接口必须 404**、未登录必须 401 |
| `tools/order-flow-test.py` | 卖家确认/拒单、买家确认收货、取消订单（含越权、重复操作、状态校验、支付/退款分支）|
| `tools/bargain-test.py` | 发起议价的全部业务校验、出价 50% 边界值、**列表数据隔离（不传 view / 伪造 sellerId）** |
| `tools/run-regression.ps1` | 上面三个的编排：检查服务 → 重置数据 → 依次执行 → 汇总 |

> ⚠️ 两个 Python 脚本需要 Python 3。Windows 上 `python` 可能是应用商店的假 stub，
> 用 `py -3` 更可靠（`run-regression.ps1` 会自动挑可用的解释器）。
>
> 数据基线脚本：[test-reset.sql](<../sql/test-reset.sql>)（订单）、
> [test-reset-bargain.sql](<../sql/test-reset-bargain.sql>)（议价）。
