## 亮点 1：二手商品只有一件 —— 怎么保证不卖两次？

**场景**

外卖项目里"一份宫保鸡丁"可以无限卖，所以**根本不存在超卖**。
但二手书只有一本：两个人同时点"下单"，如果都成功，就有一方拿不到货。

**我踩的坑**

第一版是"先查状态，再更新"：

```java
Product p = productMapper.getById(id);
if (p.getStatus() == 0) {          // ① 查：在售
    productMapper.updateStatus(id, 1);   // ② 改：交易中
}
```

两个人同时通过 ① ，然后都执行 ② → **都成功了** ✗
这是典型的"检查再行动"竞态（check-then-act）。

**方案：把"判断"放进 SQL，用影响行数当裁判**

```java
// ProductMapper
@Update("update product set status = #{toStatus} where id = #{id} and status = #{fromStatus}")
int updateStatusIfMatch(@Param("id") Long id,
                        @Param("fromStatus") Integer fromStatus,
                        @Param("toStatus") Integer toStatus);
```

```java
int rows = productMapper.updateStatusIfMatch(productId, 0 /*在售*/, 1 /*交易中*/);
if (rows == 0) {
    throw new BaseException("该商品已被他人买走");
}
```

关键在于：`where status = 0` 这个条件**在数据库里执行**，
MySQL 对同一行的更新是串行的 → 后到的那个 `where` 不成立 → `rows = 0` → 我们据此拒绝。

**为什么不用 `select ... for update`**

- 悲观锁会让"查询"也参与锁，**锁定范围大、持锁时间长**
- 我们这里只需要"检查某一行是否还是某状态" —— 条件更新把**检查和修改合成一个原子操作**，
  没有任何额外的锁开销，而且代码更短

**为什么不用分布式锁**

同理：单机 MySQL 已经能保证同一行的串行化，**加锁是多余的复杂度**（多一个 Redis 依赖点、多一种失败模式）。

**代码证据**

- `campus-server/.../mapper/ProductMapper.java` → `updateStatusIfMatch`
- `campus-server/.../service/impl/TradeOrderServiceImpl.java` → `createOrder` 里对商品状态的条件更新

**面试金句**

> "判断和修改必须在同一条 SQL 里完成 —— 我先查再改的版本，并发下两个人都会成功。"

## 亮点 2：支付回调的幂等 —— 两层防护，缺一不可

**场景**

模拟支付的回调（`paySuccess`）可能被**重复调用**：
用户连点两次、前端重试、网络重发…… 如果每次都"把订单标记为已支付"，就会重复记账。

**方案：两层**

**第一层：查询兜底（业务判断）**

```java
if (OrderConstant.PAY_PAID.equals(order.getPayStatus())) {
    throw new BaseException("订单已支付，请勿重复支付");   // 幂等：已处理过就拒绝再来一次
}
```

**第二层：唯一索引兜底（数据库约束）**

`payment_record` 表上有 **`uk_pay_no`（对 `pay_no` 支付流水号做唯一）**。
同一条支付通知重复到达时，**`pay_no` 是相同的**，第二次插入就会撞上这个唯一键：

```java
try {
    paymentRecordMapper.insert(record);
} catch (DuplicateKeyException e) {
    // 不是 bug，是兜底防线生效了 —— 说明这条支付通知已经处理过
    log.warn("支付记录重复写入，按幂等处理：orderId={}", order.getId());
    return;
}
```

> **为什么唯一键建在 `pay_no` 而不是 `order_id` 上？**
> 因为一笔订单**可以有多条流水**（支付一条、退款一条）。
> 真正"只应该出现一次"的是**同一个支付流水号**，不是订单号 ——
> 建在 `order_id` 上会把合法的退款记录也挡掉 ✗

**为什么两层都要**

| 只有第一层 | 只有第二层 |
|---|---|
| 并发下两个请求都通过检查 ✗ | 每次都要撞一次数据库异常，日志很难看 ✗ |
| | 且拿不到"业务友好"的提示 |

**第一层挡掉 99% 的重复**（顺序重试），**第二层挡住剩下 1% 的并发**（同时到达）。
这是"**能用业务逻辑挡就别靠数据库异常**，但**数据库约束必须是最后一道防线**"的典型用法。

**代码证据**

- `campus-server/.../service/impl/TradeOrderServiceImpl.java:190`（幂等判断）
- `campus-server/.../service/impl/TradeOrderServiceImpl.java:280` 附近（`DuplicateKeyException` 处理）
- `campus-server/.../mapper/PaymentRecordMapper.java`（注释写明唯一键作用）
- `sql/schema.sql` → `payment_record` 的 `uk_pay_no`

**面试金句**

> "幂等的第一层是业务查询，第二层是唯一索引 —— 只有第一层会被并发打穿，只有第二层会天天报异常。"

## 亮点 3：限时捡漏 —— Redis 预扣 + Lua，以及"补偿往哪边错才对"

**场景**

一件商品、1 个库存、几十个用户同一秒点"抢"。
如果全靠数据库，就会变成"几十个事务排队抢一行" → 数据库压力大、响应慢。

**方案：三层防御**

```
① Redis 预扣（Lua 原子脚本）   ← 流量挡箭牌：几十个请求里只有 1 个能扣到
        ↓ 只有扣到的才继续
② 数据库条件更新（防超卖）      ← 最终裁判：真的把商品状态改掉
        ↓
③ 唯一索引（防一人多单）        ← 兜底：同一用户对同一商品只能有一条记录
```

Lua 脚本保证"读库存 + 判断 + 扣减"在 Redis 里**原子执行**，
不会出现"两个请求都读到 1 然后都扣"的情况。

**最关键的一步：失败补偿的方向**

如果第 ② 步（数据库）失败了，要把 Redis 预扣的库存**加回去**。
但补偿**本身也可能失败**（Redis 挂了、网络断了）。这时怎么办？

```java
// 补偿失败时，日志级别必须是 ERROR，并且【明确写出"库存可能偏少"】
try {
    stockUtil.restore(productId);
} catch (Exception ex) {
    log.error("补偿失败！Redis 库存可能偏少，需人工核对：productId={}", productId, ex);
}
```

**推理过程（这是我当时想清楚的一件事）**：

| 补偿失败的后果 | 会造成什么问题 | 严重程度 |
|---|---|---|
| Redis 库存**偏高**（没扣成功但以为扣了）| 用户能进到第 ② 步，然后被数据库拦住 → 只是白跑一趟 | 可接受 ✓ |
| Redis 库存**偏低**（扣成功了但没加回来）| 商品明明还在售，却**永远抢不到**了 | 严重 ✗ |

**所以：补偿的方向要偏向"宁可 Redis 库存偏高"** ——
因为数据库那道守卫会兜住"偏高"，而"偏低"会让你永久丢货。
这就是我们上一轮把"补偿失败"从 `log.warn` 改成 `log.error` 的原因。

**代码证据**

- `campus-server/.../utils/FlashSaleStockUtil.java`（Lua 脚本 + 补偿）
- `campus-server/.../service/impl/FlashSaleServiceImpl.java`（`grab` 的三层流程与补偿）

**面试金句**

> "Redis 是挡箭牌，数据库是裁判。挡箭牌错了没关系，裁判错了才要命 —— 所以补偿宁可让 Redis 库存偏高。"

## 亮点 4：跑腿抢单 —— 8 个人抢 1 单，为什么我不加分布式锁

**场景**

一笔跑腿单挂在"待接单大厅"，8 个跑腿员同时点"接单"。
要求：**恰好 1 人成功**，其他人看到"已被抢走"。

**方案：单行条件更新**

```java
int rows = deliveryOrderMapper.updateStatusIfMatch(
        id, DeliveryConstant.STATUS_WAITING,   // 从"待接单"
        DeliveryConstant.STATUS_ACCEPTED,      // 改成"已接单"
        BaseContext.getCurrentId(),            // 同时写入抢到的人
        LocalDateTime.now());
if (rows == 0) {
    throw new BaseException("手慢了，这单已被别人抢走");
}
```

`update ... where id = ? and status = 0` 在 MySQL 里对同一行是**串行**的：
8 个请求排队，第一个把 `status` 改成 1，后面 7 个的 `where` 不成立 → `rows = 0`。

**为什么不用分布式锁（Redisson / ZooKeeper）**

| 分布式锁 | 条件更新 |
|---|---|
| 需要额外引入 Redis/zk 依赖 | 零额外依赖 |
| 锁超时、锁续期、误删锁等一堆边界问题 | 没有锁，就没有这些边界 |
| 有锁等待 → 用户要等 | 不等待，直接告诉结果 |

**关键认知**：
"防并发"不等于"必须加锁"。
**如果冲突只发生在同一行数据上，数据库的原子更新就是最便宜的锁** ——
它天然串行、天然释放（事务结束就释放）、天然没有死锁。

**什么时候才真需要分布式锁**

当"要保护的范围"**跨多行、跨多表、甚至跨服务**时（比如"扣库存 + 创建订单 + 发消息"作为一个整体只能有一个执行者），
单行条件更新就不够了，那时才考虑分布式锁或消息队列串行化。

**代码证据**

- `campus-server/.../service/impl/DeliveryServiceImpl.java` → `accept`
- `campus-server/.../mapper/DeliveryOrderMapper.java` → `updateStatusIfMatch`

**面试金句**

> "冲突只在一行上时，数据库的条件更新就是最便宜的锁 —— 加分布式锁反而引入了锁超时、锁续期这些新问题。"

## 亮点 5：五条状态机 —— 以及一条"守卫"的纪律

**项目里有 5 条状态机**

| 状态机 | 状态 | 谁在推进 |
|---|---|---|
| 交易订单 | 0待确认 / 1待交易 / 2已完成 / 3已取消 / 4超时取消 | 买家、卖家、定时任务 |
| 跑腿单 | 0待接单 / 1已接单 / 2取货中 / 3已送达 / 4已取消 | 跑腿员、买卖双方、管理员 |
| 议价 | 0待回应 / 1已接受 / 2已拒绝 / 3已过期 | 卖家、定时任务 |
| 投诉工单 | 0待处理 / 1处理中 / 2已完结 | 管理员 |
| 信用分 | （不是状态，是数值 + 每日额度） | 系统 + 管理员 |

**踩过的坑：守卫的角色搞反了**

定时关单任务里，我原来写：

```java
if (order.getStatus() != 0) {
    return;     // 我以为这是"不处理"
}
```

但实际上，这里我**应该**继续处理（状态为 0 才需要关单）。
写反的结果是：**所有该关的单都没关**。

**我提炼出的纪律（写进 docs/07 了）**：

> **方法开头的 `return`，语义必须是"这件事不归我管"，而不是"条件不满足"。**
> 如果语义是"我必须处理"，那条件不满足时应该 `throw`，而不是静默 `return`。

举例：
- `timeoutClose`：订单状态不是 0 → 说明"已经被别人处理了，不归我管" → `return` ✓
- `confirm`：订单状态不是 1 → 说明"用户点错了" → `throw new BaseException("订单状态异常")` ✓

**另一条纪律：终态不止一个**

"不能操作"的守卫，要把**所有终态**列全。
我在"管理员强制取消跑腿单"上就漏了：

```java
// 只拦了"已送达"
if (STATUS_FINISHED.equals(status)) { throw ...; }
// 漏了"已取消"✗
```

漏掉的后果很隐蔽：对一张已取消的单子再取消一次，
`update ... where status = 4` 会**匹配到它自己** → MySQL 返回匹配行数 1 → **接口报成功，实际什么都没发生** ✗

**代码证据**

- 各 `*Constant.java`（状态定义与名字映射）
- `campus-server/.../task/` 下的定时任务
- `docs/07-易错点与踩坑清单.md`（流程纪律 1~7）

**面试金句**

> "状态机里最容易错的两件事：守卫的 return 到底是'不归我管'还是'条件不满足'；以及终态往往不止一个。"

## 亮点 6：信用分 —— 唯一入口、上限、豁免，以及如何约束管理员

**场景**

平台需要"信誉"来支撑二手交易：好评加分、差评扣分、超时爽约重扣。
同时管理员要能人工干预（"经核实是误会，补回 5 分"）。

**三道规则 + 一个豁免**

| 规则 | 数值 | 为什么 |
|---|---|---|
| 好评 +1 / 中评 0 / 差评 -2 | 固定分值 | 惩罚要重（差评 -2 > 好评 +1），让"恶意差评"有成本 |
| 交易完成 +2 | 固定分值 | 鼓励真实成交 |
| 超时爽约 -5 | 固定分值 | 最重，因为它浪费了对方的时间和机会 |
| **每日加分上限 10** | 防刷 | 防止"自己给自己刷好评"一天刷到满分 |
| **分数下限 0** | 兜底 | 不能扣成负数（否则没法体现"谁更差"）|
| ⭐ **补偿性加分豁免上限** | 例外 | 撤销差评不是刷分行为（详见下面）|

**为什么所有变动都走唯一入口 `CreditService.changeCredit`**

如果哪里图省事直接 `update user set credit_score = credit_score + 1`：

- `credit_log` 里没记录 → **总分和流水对不上**
- "每日加分上限"失去依据（上限是靠查流水算的）
- 扣分溯源失效（用户问"我为什么被扣分"，你答不出来）

**补偿豁免（这是我在写测试时发现的一个真问题）**

```
某人今天已经加满 10 分
   ↓
管理员删掉一条恶意差评，要还他 2 分
   ↓
这 2 分如果算"今日加分" → 被上限直接吞掉 ✗
   ↓
结果：差评删了，分还是没回来 ✗ 功能等于没做
```

**根因**：`changeCredit` 把所有正向加分一视同仁，但"**撤销处罚**"根本不是刷分行为。

**修法**：加了参数 `countTowardDailyCap`
- 正常加分（完成交易 / 好评）→ `true`
- 补偿性加分（撤销差评扣分）→ `false`

**如何约束管理员的手动裁量**

| 措施 | 说明 |
|---|---|
| 理由必填 | 没有"为什么"，事后无法举证 |
| 单次幅度 ≤ ±20 | 完全放开裁量权的风险是"关系好就加 100、看不顺眼就扣光" |
| 必须走唯一入口 | 保证有流水、有上限、有下限 |
| 日志记录管理员 id | 追得到人 |

**代码证据**

- `campus-server/.../service/impl/CreditServiceImpl.java`（`changeCredit` 的两个重载）
- `campus-server/.../constant/CreditConstant.java`（分值、上限、星级阈值）
- `campus-server/.../service/impl/AdminUserServiceImpl.java` → `adjustCredit`
- `campus-server/.../service/impl/ReviewServiceImpl.java` → `deleteByAdmin`（补偿豁免的调用点）

**面试金句**

> "分数变动必须只有一个入口，否则流水和总分一定会对不上。而'撤销处罚'不该受防刷上限约束 —— 那不是刷分，是纠错。"

## 亮点 7：WebSocket 点对点推送 —— 以及那个"谁都能冒充别人"的漏洞

**场景**

买家卖家要实时聊：新消息推送、已读回执、未读数。

**基础做法**

用 `sid`（会话标识）作为 WebSocket 的路径参数：

```java
@ServerEndpoint("/ws/{sid}")
```

**我发现的漏洞**

Spring MVC 的拦截器**管不到 WebSocket 端点**（`@ServerEndpoint` 不走 MVC 的 HandlerInterceptor）。
所以 `{sid}` 里的内容**没有任何校验** —— 我可以随便填别人的 userId，
服务端就把发给别人的消息推给我了 ✗ 这是**越权读取他人私信**级别的漏洞。

**修法：连接时带 token，服务端自己解析身份**

```
ws://host/ws/{sid}?token=<用户JWT>
```

```java
// WebSocketServer.onOpen —— 两个条件的校验，缺一不可
Long tokenUserId = parseUserId(session.getQueryString());          // ① 从 queryString 解析 token
if (tokenUserId == null || !String.valueOf(tokenUserId).equals(sid)) {
    session.close();                                              // ② 解析失败，或 sid 与 token 里的人不一致
    return;
}
```

**注意第 ② 个条件**：不只校验"token 有效"，还要校验"**token 里的人 == 客户端声称的 sid**"。
只验 token 不够 —— 否则我拿自己的合法 token 配别人的 sid，就能冒充 ✗

**为什么不是"在拦截器里加个判断"**

因为请求**根本不经过拦截器** —— 这是关键认知：
**不同协议/不同组件有自己的入口，安全校验必须在各自的入口上做，不能指望一个全局拦截器包打天下。**

**代码证据**

- `campus-server/.../websocket/WebSocketServer.java`（`onOpen` 的 token 校验、`sendToUser`、三种推送类型）
- `campus-server/.../interceptor/JwtTokenUserInterceptor.java`（注释里说明了它覆盖不到 WebSocket）

**面试金句**

> "拦截器管不到 WebSocket —— 我以为加了 token 拦截就安全了，其实那个端点根本没有拦截器。"

## 亮点 8：缓存一致性 —— 分清"谁是权威"

**场景**

`user.status`（封禁）、`product` 详情等都被缓存或部分缓存在 Redis 里。
一旦数据库改了，缓存不动就会读到旧值。

**我做的一件事：先问"谁是权威数据"**

| 数据 | 权威在哪 | 缓存的作用 | 不一致的后果 |
|---|---|---|---|
| 用户封禁状态 | **数据库** | 减少每次请求查库 | 封禁后可能还能用几秒（**可接受**）|
| 捡漏库存 | **Redis**（流量闸门）| 挡掉绝大多数请求 | 偏高 → 数据库兜住 ✓；偏低 → 丢货 ✗ |
| 商品详情 | 数据库 | 加速读 | 短暂旧数据（可接受）|

**关键判断**：不是所有数据都值得"强一致"。
- 封禁状态不一致 5 分钟 → 风险可控，用**短 TTL + 主动清缓存**就够
- 库存不一致 → 直接导致"卖不出去"，必须让数据库当最终裁判

**具体做法**
- 封禁/解封时**主动删** `user_status:{id}` 这个 key（不等 TTL 过期）
- 缓存失败时**fail-open**（Redis 挂了也不能让所有人登录不了）—— 但要在日志里留痕

**代码证据**

- `campus-server/.../interceptor/JwtTokenUserInterceptor.java`（封禁检查 + 缓存 + fail-open）
- `campus-server/.../service/impl/AdminUserServiceImpl.java` → `updateStatus`（改状态后清缓存）

**面试金句**

> "先问'谁是权威'再决定要不要强一致 —— 封禁状态旧 5 分钟能接受，库存旧 5 秒就会出事。"

## 亮点 9：测试工程 —— 209 项回归，和一键复现

**做了什么**

- 10 个测试脚本、约 2200 行、**209 项断言**，覆盖全部模块

面试官问"你怎么测的"时，大部分人的回答是"我手动点了点"。
我的回答可以是：**"每个模块都有回归脚本，一键跑；测试数据有专门的 reset SQL，可以连续跑、结果稳定。"**

**我为此解决的两个真问题**

| 问题 | 现象 | 解法 |

## 亮点 10：平台治理 —— 投诉裁决与"强制操作必须留痕"

**场景**

二手交易必然有纠纷：货不对板、放鸽子、恶意差评。
平台需要"有人能裁决"，而**管理员的操作本身也必须被约束**。

**两个设计点**

**① 并发裁决：抢"处理权"而不是加锁**

两个管理员同时打开同一个投诉工单，都点"处理"：

```java
// 条件更新：只有还在"待处理"的工单才能被推进
int rows = complaintMapper.handleIfNotDone(id, handleResult, handleNote, now);
if (rows == 0) {
    throw new BaseException("该工单已被其他管理员处理");
}
```

**为什么用"抢处理权"而不是"先查再改"**：
先查再改 → 两个管理员都会看到"待处理"，都会执行 → **重复处罚**（比如信用分被扣两次）✗
条件更新 → 只有一个能推进，另一个拿到 `rows = 0` → 提示"已被处理" ✓

**② 强制操作必须能追到人**

管理员的"强制取消跑腿单""调整信用分""删除评价"这类操作，
**全部要求填原因 + 日志记录管理员 id**：

```java
log.warn("管理员强制取消跑腿单：deliveryId={}, 原状态={}, 跑腿员={}, 原因={}, 管理员={}",
        id, status, runnerUserId, reason, BaseContext.getCurrentId());
```

**为什么**：事后用户投诉"我的单子怎么没了"，平台要有举证能力。
只说"有人取消了"不够 —— 要能说"**是谁、什么时候、因为什么**"。

**代码证据**

- `campus-server/.../service/impl/ComplaintServiceImpl.java`（`handle` 的抢处理权 + 处罚联动）
- `campus-server/.../mapper/ComplaintMapper.java` → `handleIfNotDone`
- `campus-server/.../service/impl/DeliveryServiceImpl.java` → `cancelByAdmin`

**面试金句**

> "管理员的操作是最需要审计的操作 —— 权力越大的动作，越要留痕到'谁、为什么'。"

## 案例 11：统计口径错了 —— 接口返回 200，但数字是错的

**现象**：我做了个"用户主页"接口，显示某人的在售 / 已售商品数。三个测试用户返回的都是 **34 / 4**。

**排查**：拿 MySQL 直接查真实值 —— 用户 1000 应该 2/0，用户 2 应该 8/2。
三个用户一模一样 = 这是**全平台**的数字，根本不是"这个人的"。

**根因**：
```java
Map<String,Object> map = new HashMap<>();
map.put("status", 0);          // 只按状态筛，没按卖家筛 ✗
```
更麻烦的是：`countByMap` 的 SQL 里**根本没有 `sellerId` 这个条件** ——
所以我光在 Map 里加参数是无效的，**必须同时改 XML**。

**修法**：给共享查询加**可选条件**（不是必填）：
```xml
<if test="sellerId != null"> and seller_id = #{sellerId} </if>
```
因为管理端数据看板也在用 `countByMap`，改成必填会直接把看板打成 0。
改完专门回归了看板数字，确认还是 34/4。

**面试怎么讲**：
> "这类 bug 的特征是**接口不报错、返回 200、但数字是错的**。
> 它不会在日志里留任何痕迹，只能靠"拿数据库真实值对一遍"才能发现。
> 所以我后来养成一个习惯：**任何统计接口，写完先问自己'这个筛选条件够不够把别人排除掉'**，
> 然后拿两三个不同用户的数据交叉验证一遍。"

## 案例 12：Redis 里躺着旧版本的类 —— 一次很隐蔽的线上故障

**现象**：我给 `ProductVO` 加了一个字段（浏览量 / 收藏数），
本地改完、重启、刷新 —— 商品列表接口直接 500，报"未知错误"。

**排查**：全局异常处理器把真实异常吞了，只返回一句"未知错误"。
把日志级别调到 DEBUG 才看到真身：
```
java.io.InvalidClassException: com.campus.vo.ProductVO;
  local class incompatible: stream classdesc serialVersionUID = -1234..., local class serialVersionUID = 5678...
```

**根因**：商品列表被**缓存在 Redis 里**（JDK 序列化的 `List<ProductVO>`）。
我给类加了字段 → **默认计算的 `serialVersionUID` 变了** → 反序列化时对不上 → 抛异常。

**修法**：
1. 给 `ProductVO` 显式声明 `private static final long serialVersionUID = 1L;`
2. 把 Redis 里那份旧缓存删掉（用原始 RESP 协议连上去 `DEL`，因为那台机器上 `redis-cli` 跑不起来）

**学到什么**：
> **"凡是会被缓存/持久化的类，都应该显式声明 `serialVersionUID`"** ——
> 不声明的话，编译器会按类的结构算一个哈希值，**加一个字段就变** ✗
> 更坑的是：异常信息被全局异常处理器吞成了"未知错误"，**排查方向完全跑偏**。
> 后来我给全局异常处理器加了一条：**未预期的异常必须打完整堆栈**。

## 案例 13：缓存 key 的粒度 —— "我改了库，为什么只有一个分类变了？"

**现象**：我直接改数据库，把商品图换了一批。刷新页面 ——
"全部"那一栏是新的 ✓ **点进具体分类还是旧图** ✗

**根因**：列表缓存的 key 是 **`product_list_<categoryId>`** ——
有 1 个 null（全部）+ 8 个分类，**共 9 个 key**。我只 `DEL` 了 null 那一个。

`DEL` 返回 `:9` 的时候我才反应过来 —— 确实是 9 个。

**修法**：立刻清全部 9 个 key；把"清缓存"写进重灌数据的脚本里。

**学到什么**：
> 1. **应用内部的缓存失效是"改数据的同时清缓存"**（管理端审核、卖家编辑都会 `cleanCache`）；
>    但我这次是**绕过应用直接改库** —— 缓存当然不知道要失效。
> 2. **缓存 key 的设计要考虑"怎么整体失效"**。按分类分 key 查询效率高，但清理成本也高。
>    更稳的做法是**在 key 里带版本号**（`product_list_v2_<catId>`），换数据版本时整体自然失效。

## 案例 14：数据最小化 —— 公开接口不能直接把实体返回出去

**背景**：做"用户主页"时，我一开始想直接把 `User` 实体返回给前端。

**问题**：`User` 实体上有 `openid`、`realName`、`studentNo`、`studentCardImg`、`phone` ——
这个接口是**任何登录用户都能调的**，直接把实体返回 = 泄露别人的学号、手机号、学生证照片。

**做法**：专门建了一个 `UserProfileVO`，只放**能公开**的 10 个字段：
```
userId / nickname / avatar / role / creditScore /
goodReviewCount / badReviewCount / onSaleCount / soldCount / joinedDays
```
并且在 VO 的注释里写明："这五个字段一个都不能加进来，加了就是事故"。

**验证**：写了一条断言，直接拿接口返回的 JSON 文本去搜 `openid` / `phone` / `studentNo` 这些关键词，
**一个都不能出现**。

**面试怎么讲**：
> "这是数据最小化原则的具体落地：**不要直接把实体返回给前端**，
> 而是用一个专门的 VO，明确列出"这个场景下哪些字段可以被看到"。
> 好处是：以后有人给实体加字段，也不会意外泄露出去。
> 我还加了一条自动化检查 —— 扫接口原始响应里有没有敏感关键词。"

## 案例 15：测试的时序假设 —— 两个推送帧，顺序不保证

**现象**：全量回归里，私信模块偶发挂 2 项（WebSocket 推送），**重跑有时只挂 1 项**。

**先判断"是不是功能坏了"**：不是 ——
- "能拉到聊天记录"✅ → 消息存库成功
- "小明收到已读回执"✅ → 推送机制本身是通的

**根因**：小明发消息后，服务端会推**两帧**（`type=message` 和 `type=unread`），
这两帧走**不同的发送路径**，**到达顺序没有保证**。
而测试写的是"第 1 帧断言 message、第 2 帧断言 unread" —— 顺序一反过来，两项一起挂。

**修法**：8 秒内把收到的帧都收集起来，只断言"**两种 type 都出现过**"，与顺序无关。
失败时把收到的类型列表打出来（`收到 2 帧：['message', 'unread']`），下次再出问题一眼能看出差哪帧。

**学到什么**：
> **异步 + 多消息的场景，测试不能假设顺序** ✗
> 正确做法是"**收集 + 集合断言**"（`set` 里有没有这些元素），而不是"第 N 个是什么"。
> 另外：**"偶发失败"要第一时间判断"是环境/时序问题还是逻辑问题"** ——
> 看"全挂还是零星挂"、"换个跑法还挂不挂"，能省很多时间。

## 案例 16：改"源"还是改"产物" —— 演示数据被重灌打回原形

**现象**：我把商品图换成了真实图床（picsum）的照片，页面显示正常。
第二天重灌演示数据（`reseed-demo.ps1`）—— **图片全变回了本地的几何插画**。

**根因**：我是**直接改数据库**的（`UPDATE product SET images = ...`），
而**生成器 `gen-demo-data.py` 里那条 UPDATE 还是旧的**（指向本地 SVG）。
重灌 = 重新执行生成器 → 又把库改回去了。

**同一天还有一次一模一样的错**：我改了商品分类（把"高数"从"服饰鞋包"挪到"教材书籍"），
只改了库、没改生成器里的 `CAT_FIX` → 重灌又错位。

**修法**：**改生成器，然后重新生成**，而不是改库。

**学到什么**：
> **只要存在"可以重新生成"的东西，就必须改"源"，不能改"产物"。**
> 数据库是产物、生成器是源；`target/` 是产物、`src/` 是源；
> 打包后的 jar 是产物、源码是源。
> 这跟"缓存"是同一类问题：**改了下游、忘了上游，下次生成就打回原形**。
