# 03 · 删除影响分析与批次计划

> **为什么要先做这个**：施工图 §2.1 列了 7 类要删的东西，但盲删必然编译爆炸。
> 本文基于对 **173 个源文件**（java + xml）的逐符号引用扫描，给出有依据的删除批次。
> 扫描时间：改造前基线（`sky_take_out` 版本源码）。

---

## 一、三个核心结论（都有引用证据）

### 结论 1：`OrderServiceImpl` 是枢纽，订单相关的删除不能拆散做

`OrderServiceImpl` 同时引用了：`ShoppingCart`、`OrderDetail`、`AddressBook`、`WeChatPayUtil`、支付回调相关逻辑。

也就是说，**购物车 / 订单明细 / 地址簿 / 支付这四类东西，全都长在订单服务上**。
如果阶段 2 就动它们，你得在 `OrderServiceImpl` 上反复做手术；而阶段 3 要把它整体重写成
`TradeOrderServiceImpl`——**那次重写才是正确的手术时机**。

### 结论 2：报表簇和套餐簇必须在 mapper 改名之前删掉，否则编译必炸

这是本次扫描最重要的发现，有直接的编译级依赖：

```
WorkspaceServiceImpl.java:5   import com.campus.mapper.DishMapper;
WorkspaceServiceImpl.java:6   import com.campus.mapper.OrderMapper;
WorkspaceServiceImpl.java:7   import com.campus.mapper.SetmealMapper;
WorkspaceServiceImpl.java:24  public class WorkspaceServiceImpl implements WorkspaceService
WorkspaceServiceImpl.java:153 setmealMapper.countByMap(map)

ReportServiceImpl.java:6      import com.campus.mapper.OrderMapper;
ReportServiceImpl.java:37     private OrderMapper orderMapper;
ReportServiceImpl.java:153    ... Orders.COMPLETED
```

我们阶段 2 要把 `DishMapper`→`ProductMapper`、`Orders`→`TradeOrder`。
只要报表/工作台还活着，这两处改名就会**编译失败**。所以它们不是"可以延后"，而是**必须在前**。

好消息：这两簇**入向引用极少**，是干净的独立簇：

| 簇 | 入向引用 | 说明 |
|---|---|---|
| 报表 | 仅 `ReportController` → `ReportService` → `ReportServiceImpl` | 自闭环 |
| 工作台 | 仅 `WorkSpaceController` → `WorkspaceService` → `WorkspaceServiceImpl`；`ReportServiceImpl` 依赖 `WorkspaceService` | 自闭环 |

### 结论 3：XML 里的表名/列名，编译器不管，只在运行时炸

`DishFlavorMapper.xml`、`SetmealMapper.xml` 这些文件里的 `setmeal_dish`、`dish_flavor` 是**字符串**，
删掉实体类后项目照样编译通过、照样能启动——直到某个接口被调用才抛
`Table 'xxx.dish_flavor' doesn't exist`。**这类问题只能靠搜索确认，不能靠编译发现。**

已确认引用了"待删表"的 XML（36 处匹配）：

| XML 文件 | 引用的表/列 |
|---|---|
| `SetmealMapper.xml` | `setmeal`（含 join category） |
| `SetmealDishMapper.xml` | `setmeal_dish` |
| `DishFlavorMapper.xml` | `dish_flavor` |
| `ShoppingCartMapper.xml` | `shopping_cart`、`dish_flavor` |
| `OrderDetailMapper.xml` | `setmeal_id`、`dish_id`、`dish_flavor` 列 |
| `AddressBookMapper.xml` | `address_book` |
| `OrderMapper.xml` | `address_book` |

### 批次 B —— 阶段 2：删套餐簇 + 口味簇（与 `Dish→Product` 重写同批）

**为什么必须同批**：`DishServiceImpl` 直接依赖 `SetmealDishMapper` 和 `DishFlavorMapper`：

```
DishServiceImpl.java:12  import com.campus.mapper.DishFlavorMapper;
DishServiceImpl.java:14  import com.campus.mapper.SetmealDishMapper;
DishServiceImpl.java:92  setMealDishMapper.selectSetmealIdsByDishIds(ids)   // 删除菜品前校验是否被套餐引用
DishServiceImpl.java:111 dishFlavorMapper.selectByDishId(id)
```

而 `DishServiceImpl` 本来就要被改写成 `ProductServiceImpl`（二手商品没有口味、没有套餐），
所以**"改 Dish" 和 "删套餐/口味" 是同一件事的两面**。

**删除文件**

```
entity:  Setmeal / SetmealDish / DishFlavor
dto:     SetmealDTO / SetmealPageQueryDTO / DishFlavorDTO
vo:      SetmealVO / SetmealPageVO
mapper:  SetmealMapper(.xml) / SetmealDishMapper(.xml) / DishFlavorMapper(.xml)
service: SetmealService / SetmealServiceImpl
ctrl:    controller/admin/SetmealController / controller/user/SetmealController
except:  campus-common/.../exception/SetmealEnableFailedException
```

**必须手工修改的文件**

| 文件 | 要改什么 |
|---|---|
| `MessageConstant.java` | 删掉 `SETMEAL_ENABLE_FAILED` 等套餐相关常量 |
| `DishServiceImpl.java` | 去掉口味逻辑、去掉 `setMealDishMapper` 校验（此文件将重写为 `ProductServiceImpl`） |
| `DishDTO.java` / `DishVO.java` | 去掉 `flavors` 字段（将重写为 `ProductDTO` / `ProductVO`） |

**风险点**：`ShoppingCartMapper.xml`（批次 C）和 `OrderDetailMapper.xml` 里有 `dish_flavor` / `setmeal_id`。
**它们此时不会被删**，编译不受影响，但只要跑到购物车/下单接口就会炸。
→ 所以批次 B 之后，**阶段 2 不要测试购物车和下单功能**；这两块在阶段 3 统一重写。
建议在 `application-dev.yml` 同级放个提醒，或者干脆把这两个 XML 里的相关列先注释掉（可选）。

**验证**：编译通过 → 启动 → 用户端 `/user/setmeal/*` 404（预期）→ 商品相关接口不受影响。

| 批次 | 阶段 | 内容 | 前置依赖 | 删除文件数（已核对） |

**铁律**：每批做完立刻 `mvn -o clean compile` + 启动一次。**不要跨批攒着改**——
这是你自己笔记里"小增量开发"的实践：一次只改一小段，出错范围极小。

## 四、执行前提醒

1. **数据库表先不要 DROP**。`sky_take_out` 库完整保留作对照，新库建 `campus_second_hand`。
   万一改造翻车，旧库旧代码都能回退。
2. **删除用 git**，每批一个 commit：
   ```
   git add -A
   git commit -m "阶段2-批次A：移除报表与工作台模块"
   ```
   删错了 `git checkout -- <file>` 就能救回来。
3. **不要用 IDEA 的 "Safe Delete" 全局删**——它会把 `OrderServiceImpl` 里还在用的引用一起删掉，
   反而破坏编译。按批次清单手工删，删完看编译器报什么，再逐个处理。
4. 每批删完，**用 `git status` 确认没有意外文件被删**（比如误删 `Result.java` 这种骨架）。
