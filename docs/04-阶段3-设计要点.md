## 一、私信权限矩阵（对应阶段 1 缺口 4）

### 1.1 权限规则（来自需求）

| 商品类型 | 阶段 | 谁能给谁发消息 | 依据 |
|---|---|---|---|
| 普通闲置 | 在售 / 交易中 | 买卖双方可一对一私信 | 需求：普通商品可私聊沟通细节 |
| 捡漏商品 | **预热期**（发布后～抢购开始） | **都不能发**（方案 B） | 需求：抢购前关闭私信，页面只展示商品描述 |
| 捡漏商品 | 抢购结束·窗口期内 | **仅抢到的买家 → 卖家** | 需求：10 分钟窗口期沟通交付 |
| 捡漏商品 | 窗口期过期 / 已取消 | **关闭** | 需求：订单取消后私信通道随之关闭 |
| 任意商品 | 交易完成后 | 可保留（用于售后沟通） | 建议：与投诉工单配合 |

### 1.2 关键结论：权限是「会话级」的，不是「消息级」的

`message` 表只有 `from_user_id` / `to_user_id`，**判不出"这两人在聊哪件商品"**，权限无从校验。
两条路可选，你选一条并说明理由：

**方案 A：给 message 加 `product_id`**
- 优点：改动最小，一张表搞定
- 缺点：会话身份变成三元组 `(买家, 卖家, 商品)`，每次发消息都要查商品状态 + 抢购状态 + 时间窗；
  "会话是否已关闭"没有地方存，只能每次现算；历史消息按会话聚合要靠 group by

**方案 B（推荐）：新增 `conversation` 会话表，`message` 挂 `conversation_id`**

```
conversation: id, product_id, buyer_id, seller_id, order_id(null),
              status tinyint(0开放 1已关闭), can_send_until datetime(null),
              create_time, update_time
message:      id, conversation_id, from_user_id, to_user_id, content, msg_type, is_read, ...
```

- 优点：**权限判定收敛到一处**（查会话 status + can_send_until），商品类型/抢购阶段只在"创建会话"时判断一次；
  `can_send_until` 直接承载 10 分钟窗口期；历史消息按 `conversation_id` 查询，天然适合分页
- 缺点：多一张表、多一次关联

> **面试口径**：为什么单独建会话表？因为"能否发消息"是会话的属性（有生命周期、有有效期），
> 不是单条消息的属性。放在消息表上会导致每条消息都要重算一遍业务状态。

⚠️ **决策点 1**：选 A 还是 B？选 B 的话，`conversation` 表要补进 `schema.sql`（阶段 1 的 11 张表会变 12 张）。

### 1.3 WebSocket 设计要点

- **握手鉴权**：连接地址带 token（`/ws/{token}` 或 query 参数），握手时解析 `userId`，
  校验通过才 `sessionMap.put(userId, session)`；否则直接关闭连接
- **会话存储**：`ConcurrentHashMap<Long, WebSocketSession>`（单实例够用；多实例需 Redis 广播，可作为面试加分点提）
- **消息流转**：收到消息 → 敏感词过滤 → **先落库** → 查对端 session → 在线则推送，离线则只落库
- **历史消息**：客户端上线后主动拉取（`GET /user/message/history?conversationId=..&page=..`），不靠推送补历史
- ⚠️ **决策点 2**：现有 `WebSocketServer` 的真实状态（已核对源码，别凭印象）：

  | 事实 | 说明 |
  |---|---|
  | `@ServerEndpoint("/ws/{sid}")` | 连接路径带的是 **sid**，不是 userId |
  | `sessionMap<String, Session>` | key 是 sid → **当前无法按用户定向推送** |
  | `onMessage` 只 `System.out.println` | **完全没有私信逻辑**，收到消息什么都不做 |
  | `sendToAllClient(...)` | 只有群发方法，被 `OrderServiceImpl` 两处调用（228、535 行，下单后群发催单） |

  所以它不是"要清理掉一堆旧业务逻辑"，而是一个**只有连接管理和群发的骨架**。两条路：
  - **复用改造**：key 从 sid 换成 userId，实现 `onMessage`（落库+点对点转发），保留 `sendToAllClient` 给系统通知用
  - **新建 `ChatWebSocketServer`**：私信与系统通知分离，职责更清晰

  我倾向**复用改造**（骨架本来就该干这个），但你要注意：改了 key 的含义以后，
  `OrderServiceImpl` 那两处群发调用要一起确认是否还需要（下单催单在二手平台未必有意义）。

## 二、议价状态机（仅普通商品）

### 2.1 状态定义（沿用阶段 1 规格）

```
0 待处理   1 买家出价   2 卖家还价   3 已接受   4 已拒绝   5 已过期
```

### 2.2 流转规则

```
                    ┌─────────────────────────────────────┐
                    │  买家发起议价（出价 ≥ 标价×50%）      │
                    └───────────────┬─────────────────────┘
                                    ▼
                            status=1 买家出价
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      卖家【接受】            卖家【还价】            卖家【拒绝】
              │                     │                     │
              ▼                     ▼                     ▼
        status=3 已接受       status=2 卖家还价      status=4 已拒绝
              │                     │                     │
              ▼                     ▼                     ▼
   生成预订单(order_source=2)   ⚠️ 见决策点 3        24h 内禁止再次议价
   回填 bargain.order_id
   商品状态 → 交易中
```

### 2.3 必须处理的边界

| 场景 | 处理 |
|---|---|
| 出价低于标价 50% | 拒绝，抛业务异常 |
| 卖家买自己的商品 | 拒绝（下单/议价都要校验 `buyer_id != seller_id`） |
| 商品已售罄 / 已下架 / 已是交易中 | 拒绝，抛业务异常 |
| 同一买家重复议价同一商品 | 存在未完结议价记录时拒绝 |
| 被拒绝后 24h 内再次议价 | 查询最近一条 bargain，拒绝 |
| 议价成功但订单超时未确认 | 订单超时取消 → 商品状态回退「在售」，bargain 保持不变（已接受） |
| **多轮还价** | ⚠️ 见决策点 3 |

⚠️ **决策点 3（这条最重要）**：`bargain` 表只有一组 `buyer_offer` / `seller_counter_offer` 字段，
**只能记录一轮出价**。如果卖家还价后买家想再还一次，就存不下了。三条路：

- **A. 单轮制（推荐，最简）**：卖家还价 → 买家只能【接受】或【拒绝】，不能再还价。
  状态 2 之后只允许转向 3 或 4。好处：字段够用、逻辑闭环、面试好讲；代价：灵活性低
- **B. 多轮制**：每轮出价插一条新记录（`bargain` 变成流水表），加 `round` 字段，
  查询时取最新一条 + 历史列表。好处：支持真实砍价；代价：状态机变复杂
- **C. 覆盖式**：始终更新同一条记录，覆盖旧出价。好处：改动小；代价：**丢失议价历史**（被投诉时无法举证）

**我推荐 A**，理由是：实习项目的目标是"逻辑闭环、能被追问不倒"，而不是功能最全。
但你要能说清另外两个方案为什么不选——这就是面试加分点。

## 三、订单状态机

### 3.1 状态与来源

```
order_source: 1 普通直接下单   2 议价生成   3 捡漏抢购
status:       0 待确认   1 待交易   2 已完成   3 已取消   4 超时取消
```

### 3.2 流转

```
创建订单 ──> 0 待确认 ──卖家确认──> 1 待交易 ──双方完成──> 2 已完成(finish_time)
                │                       │
                ├─ 买家/卖家取消 ─> 3 已取消
                └─ 超时未确认 ────> 4 超时取消（expire_time 到期）
```

| 来源 | 超时时长 | 依据 |
|---|---|---|
| 捡漏抢购（source=3） | **10 分钟** | 需求：抢到后 10 分钟内确认 |
| 议价生成（source=2） | 30 分钟 | 需求：普通订单 30 分钟卖家未确认自动取消 |
| 普通下单（source=1） | 30 分钟 | 同上 |

### 3.3 商品状态联动（最容易漏的地方）

```
下单/议价成功/抢购成功 → product.status = 1 交易中
订单完成              → product.status = 2 已售罄
订单取消/超时         → product.status = 0 在售（捡漏商品是否回捡漏池要单独判断）
```

⚠️ **决策点 4**：捡漏订单超时取消后，商品是"回捡漏池等下一轮抢购"还是"转为普通商品上架"？
需求原文说"重新回到捡漏池，等待下一轮抢购"。那么 `flash_start_time` 要重新设置吗？
（提示：如果不重设，抢购时间已过，用户再点抢购就会出现"活动已结束"的矛盾状态——这个坑你要自己发现并给方案。）

### 3.4 定时任务改造（已核对源码，不是凭印象）

现有 `OrderTask` 有**两个**任务，改造后两个都要动：

**任务 1：`handleTimeoutOrders`（每分钟，cron `0 * * * * ?`）**

当前实现（顺手核对过源码）：

```java
Integer count = orderMapper.cancelExpiredOrders(
        MessageConstant.TIMEOUT_CANCEL_ORDER,   // "订单超时未支付，自动取消"
        now, now.minusMinutes(15), Orders.CANCELLED);
```

对应 SQL（`OrderMapper.cancelExpiredOrders`）：

```sql
update orders set status=?, cancel_reason=?, cancel_time=?
where status = 1 and pay_status = 0 and order_time < ? limit 200
```

改造要点（**不能照抄原 SQL**）：

| 现在 | 改造后 |
|---|---|
| `status = 1 and pay_status = 0`（待付款） | `status = 0`（待确认）——我们没有支付环节 |
| `order_time < now-15min` 固定 15 分钟 | `expire_time < now`，**用订单自己的截止时间字段** |
| 取消原因文案「订单超时未支付」 | 改为「订单超时未确认」 |
| 只有一种超时时长 | 捡漏 10 分钟 / 普通 30 分钟 → 由创建订单时写入的 `expire_time` 区分，扫描逻辑无需分支 |

> 最后一行的设计好处：**超时时长差异在"写入时"解决，而不是在"扫描时"判断**。
> 扫描 SQL 只管 `expire_time < now`，简单且不会漏。面试可以讲这个取舍。

**任务 2：`processDeliveryOrders`（每天 1:00，cron `0 0 1 * * ?`）**

当前实现：把「派送中」超过 60 分钟的订单直接置为已完成。

改造要点：新的跑腿模型里，**配送状态在 `delivery_order.status`，不再挂在订单上**。
这个任务要么删掉、要么改成扫描 `delivery_order`（`status=2 取货中` 超时 → 告警或置异常）。
⚠️ 注意：**订单的「已完成」应该由买卖双方确认产生，不能由定时任务替用户拍板**——
原逻辑是外卖场景（骑手送达即完成），二手面交场景不适用。这是个很好的面试素材：*"我为什么删掉了原有的自动完成逻辑"*。

## 四、限时捡漏抢购设计（项目技术亮点核心）

### 4.1 Redis Key 设计

| Key | 类型 | 含义 | TTL |
|---|---|---|---|
| `flash:stock:{productId}` | String | 剩余库存（捡漏固定 1） | 抢购结束后 1h |
| `flash:buyer:{productId}` | String | 抢购成功的 userId（幂等判定） | 同上 |
| `flash:join:{productId}` | Set | 参与抢购的 userId 集合（统计用） | 同上 |
| `lock:flash:{productId}` | String | 分布式锁（`SET NX PX 5000`，value 用 UUID） | 5s |

> 命名规范：`业务:对象:{id}`。面试问"你的 Redis key 怎么设计的"，答"分命名空间 + 按业务对象隔离 + 明确 TTL"。

### 4.2 抢购流程（防超卖的关键）

```
1. 前置校验：商品存在、is_flash_sale=1、flash_start_time 已到、status=0
2. 幂等校验：flash:buyer:{productId} 已存在 → 直接返回"已抢完"
3. Lua 脚本原子执行（不可拆成多条命令！）：
      if redis.call('exists', KEYS[2]) == 1 then return 0 end      -- 已有人抢到
      if redis.call('get', KEYS[1]) <= 0 then return -1 end        -- 无库存
      redis.call('decr', KEYS[1])                                  -- 扣库存
      redis.call('set', KEYS[2], ARGV[1])                          -- 记录买家
      return 1
4. 成功 → 创建订单(order_source=3, expire_time=now+10min) + 写 flash_sale_record(is_success=1)
   失败 → 写 flash_sale_record(is_success=0)（记参与行为，用于统计）
5. 订单创建异常 → 补偿：库存加回、删除 flash:buyer（保证 Redis 与 DB 最终一致）
```

**三个必须能讲清的点**：

1. **为什么用 Lua 而不是分开写 exists / decr？** Redis 单线程执行 Lua 脚本期间不会插入其他命令，
   保证"判断 + 扣减 + 记录"三步原子；分开写会出现两个请求都判断为"有库存"然后都扣减 → 超卖。
2. **为什么还要分布式锁？** Lua 已解决超卖，锁主要防"同一用户并发重复提交"和"下单逻辑重复执行"。
   （如果你只做 Lua，面试被问"那还要锁干嘛"要能答上来；反之亦然）
3. **Redis 扣减成功但数据库写入失败怎么办？** 补偿 + 最终一致性，不能假装不存在这个问题。
   这是面试官最爱追问的"一致性"问题。

⚠️ **决策点 5**：项目**没有引入 MQ**。抢购成功后的下单是：
- **A. 同步创建**（Lua 成功后直接在事务里建订单）——简单，但高并发下 DB 压力大
- **B. `@Async` 线程池异步创建**——不需要额外中间件，能讲"异步削峰"，但事务边界要小心
- **C. 引入 RabbitMQ**——最"标准"，但增加部署依赖和学习成本

建议 **B**，面试时说清"C 是生产环境的做法，本项目为控制复杂度用线程池异步 + 补偿"。

### 4.3 抢购时间窗设计

- 抢购前：商品可浏览、可收藏，`POST /user/flashSale/{productId}` 返回"活动未开始"
- 抢购中：允许抢购
- 抢购结束：返回"活动已结束"

判定依据建议：`flash_start_time` + 一个活动时长（比如 1 小时），或抢购成功即视为结束。
⚠️ 这里和决策点 4 联动：**活动结束的定义要先定清楚，状态机才自洽。**

## 五、敏感词过滤（商品发布 + 私信）

- **实现方式**：DFA（确定有限自动机）/ Trie 树，一次构建多次匹配，时间复杂度 O(n)
- **词库**：本地文件（如 `resources/sensitive-words.txt`），启动时加载构建 Trie
- **为什么不用 `String.contains` 循环遍历词库**：词库上万条时每次都全量扫描，性能不可接受
- **面试口径**：能说清 Trie 的构建与匹配过程，比"我调了个第三方 SDK"高一个档次
- ⚠️ 注意：需求里说捡漏商品**预热期关闭私信**，所以敏感词过滤主要作用于**普通商品私信**和**商品发布**

## 六、跑腿模块设计（补齐）

### 6.1 与主交易订单的关系

```
trade_order (1) ──── (1) delivery_order
   deal_type=1 表示走跑腿；创建订单时同步生成跑腿单
```

- `delivery_order.trade_order_id` 关联主订单，**不冗余存 buyer/seller/product**（阶段 1 规格已定）
- 既然是一对一，建议给 `trade_order_id` 加**唯一索引**（防止重复生成跑腿单）——阶段 1 规格里只写了普通索引，这是可优化点
- 跑腿员身份：`user.role = 1` 且 `status = 0`

### 6.2 状态机

```
delivery_order.status: 0 待接单  1 已接单  2 取货中  3 已送达  4 已取消

0 待接单 ──跑腿员抢单──> 1 已接单 ──确认取货──> 2 取货中 ──确认送达──> 3 已送达
   │                      │                    │
   └──────────────────────┴────────────────────┘
                   任一环节可取消（买家取消 / 管理员介入）──> 4 已取消
```

注意：`3 已送达` ≠ 主订单完成。**主订单的「已完成」仍要买卖双方确认**（对应 §3.4 里删掉自动完成的理由）。

### 6.3 并发抢单（本节是最有技术含量的点）

多个跑腿员同时点"接单"，必须只有一个成功。三种实现：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 条件更新（推荐）** | `update delivery_order set runner_user_id=#{uid}, status=1 where id=#{id} and status=0 and runner_user_id is null`，判断 affected rows == 1 | 一条 SQL 搞定，靠数据库行锁保证原子；最轻 |
| B. 乐观锁 | 加 `version` 字段，`where version=#{v}` | 需要改表结构，且这里没有"读-改-写"的跨请求场景 |
| C. Redis 分布式锁 | `lock:delivery:{orderId}` | 杀鸡用牛刀，除非要跨多资源操作 |

**面试口径**：抢单是"单行条件更新"的典型场景，数据库的行级锁已经保证了原子性，
没必要上分布式锁；分布式锁适合"跨多个资源 / 长事务 / 非数据库资源"的场景。
> 这种"能不上锁就不上锁、能不用分布式就不用分布式"的判断，比会背 Redis 锁更能体现工程素养。

### 6.4 必须校验的边界

| 场景 | 处理 |
|---|---|
| 非跑腿员（role≠1）接单 | 拒绝 |
| 跑腿员接自己的订单（是买家或卖家） | 拒绝（自己给自己跑腿） |
| 已封禁用户（status=1） | 拒绝 |
| 订单已被别人抢走 | 条件更新 affected=0 → 返回"手慢了，已被接单" |
| 主订单已取消 | 拒绝（跑腿单也要联动取消） |

### 6.5 计价规则

需求原文：3 公里内 5 元，每超 1 公里加 1 元。

**关键设计**：`delivery_fee` 在**创建跑腿单时算好并落库**（计费快照），不要每次查询实时算。
理由：计费规则以后改了，历史订单金额不能被改动。

⚠️ **决策点 6**：距离从哪来？
- **A. 复用百度地图 API**：项目里 `BaiduMapUtil` 已经在用（配送范围校验），`sky.shop.ak` 已配置 → 可查两点距离
- **B. 简化档位**：按"起终点所属区域"固定档位（宿舍区→教学楼=5元），不依赖外部 API
- A 更真实但依赖外网可用性（**注意：本机受限环境下外网 HTTPS 从某些进程不可用，之前踩过**）；
  B 简单可靠，面试时说清"A 是生产做法，本项目为可演示性用 B"也完全站得住

### 6.6 收入结算

需求说"跑腿完成后结算跑腿员收入"，但平台**不做资金流转**（阶段 2 施工图已定：删掉微信支付）。
所以：
- **不做真实结算/提现**，只做**统计展示**：跑腿员累计跑腿费、已完成单数
- 若需要流水，加可选表 `delivery_income`（非核心，实习项目可不做）
- 面试口径：平台定位是撮合，不介入资金；收入是"记录"而非"账户余额"

## 九、支付模块（已决定要做 · 2026-10-10 补充）

> 完整决策记录见 `docs/决策记录.md` 的「〇、已拍板的决定」。这里只列实现要点。

### 9.1 档次与流程（已定）

- **档次**：第 ② 档 —— **模拟支付通道 + 担保交易**（真实资金通道需要企业资质与资金池合规，做不到）
- **流程**：**方案 A「下单即支付」**（同闲鱼/转转）
- **超时**：普通订单 15 分钟；捡漏订单 10 分钟（与抢购窗口一致）

```
下单 → 【待支付】--支付成功(进托管)--> 【待确认】卖家确认
     → 【待交易】面交验货 → 买家确认收货 → 【已完成】放款给卖家
     └ 15 分钟未支付 → 超时取消，商品重新上架
```

**为什么选方案 A（而不是"卖家确认后再支付"）**：

- 与闲鱼/转转一致，用户习惯、面试官熟悉
- **能最大化复用原工程代码**：原有"未支付超时自动取消"定时任务几乎原样可用
- 状态环节更少（4 步 vs 5 步）
- 方案 B 的致命问题：卖家确认后买家不付钱 → 商品被锁、卖家白等，还得再加一套支付超时
- 方案 A 能挡住"随便点一下就把商品占住"（校园二手平台很容易被玩坏的点）

### 9.2 表结构变更（阶段 1 的 schema 需要补）

| 变更 | 内容 |
|---|---|
| `trade_order` 加字段 | `pay_status tinyint`（0未支付 1已支付 2已退款）、`pay_time datetime`、`pay_no varchar(64)` **唯一索引** |
| 新增表 `payment_record` | 支付流水/托管记录：`id, order_id, pay_no, amount, pay_type(1支付 2退款), status, create_time, update_time` |

> `pay_no` 加唯一索引是**回调幂等的兜底**：重复通知插入同一条流水会撞唯一键，从而避免重复处理。
> 订单状态继续用 `status` 表达，支付状态用独立字段（与苍穹外卖原设计一致），
> 好处是订单状态机不用改，只多一个维度。

### 9.3 实现清单（6 项，打星号的是面试重点）

1. 订单表加支付字段 + 建 `payment_record` 表
2. `发起支付` 接口 + `支付结果通知` 接口（模拟回调）
3. ⭐ **回调幂等**：重复通知不重复处理
4. **担保逻辑**：付款进托管 → 确认收货后放款
5. ⭐ **超时未支付自动关单**：**可直接复用原 `OrderTask.handleTimeoutOrders`**，
   把判定条件从 `status=1 and pay_status=0 and order_time < now-15min`
   改为 `status=0 and pay_status=0 and expire_time < now`（超时时长由下单时写入的 `expire_time` 决定）
6. 取消订单 → 模拟退款记录（写 `payment_record` 一条退款流水 + `pay_status=2`）

### 9.4 与原有代码的关系

| 原有内容 | 处理方式 |
|---|---|
| `WeChatPayUtil` | 保留不动（真实通道的工具类），模拟通道不调用它 |
| `PayNotifyController` | 改造为「模拟支付结果通知」入口（去掉微信验签，保留幂等与状态流转） |
| 支付相关 DTO/VO | 按新字段调整，不删除 |
| `application-dev.yml` 的 wechat 配置 | 暂时保留（模拟通道用不到，留着不影响启动） |

**面试口径**（背这个）：

> "支付是模拟通道——微信支付需要企业资质，学生项目拿不到。但完整链路我实现了：
> 下单创建支付单 → 模拟支付成功 → 回调通知 → 回调幂等校验 → 订单状态流转 →
> 资金进托管 → 确认收货后放款。重点在回调幂等：支付平台的通知可能重复送达，
> 我用支付流水号做唯一约束，重复通知直接返回成功但不会重复处理。
> 接真实通道只需把模拟那一步换成 SDK 调用，其余逻辑不用改。"
