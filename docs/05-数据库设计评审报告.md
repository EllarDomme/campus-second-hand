# 05 · 数据库设计评审报告（针对豆包那份建表脚本）

> **评审对象**：你和豆包对话中产出的 11 张表建表脚本（`docx` 末尾那份完整 SQL）
> **评审方法**：① 重排换行后在 MySQL 8.0.45 上**实际执行** ② 逐模块对照需求 ③ 用真实数据验证隐患
> **结论**：**脚本能跑、基础规范合格，但相对你自己定的需求有 6 个 P0 缺口**（不补就无法实现需求）

---

## 一、总体结论

| 维度 | 评价 |
|---|---|
| 能否执行 | ✅ **11 张表零报错建成**，排序规则全部 `utf8mb4_unicode_ci` |
| 基础规范 | ✅ 全部合格（bigint 主键、decimal 金额、tinyint 状态、无物理外键、双时间字段、注释齐全） |
| 需求覆盖度 | ⚠️ **6 处 P0 缺口**：管理员表、捡漏审核状态、新旧程度、交易地点、私信会话维度、信用分流水 |
| 数据完整性约束 | ⚠️ **3 处缺唯一约束**（实测可插入重复数据） |
| 索引设计 | ⚠️ 2 处不合理（实测走不到索引 / 用不上复合索引） |

**一句话**：这份 schema 的"骨架规范"是对的（这部分豆包教得没问题），但**它是按"11 个实体"推出来的，没有回头对照你自己写的 11 个业务模块**——缺的字段全在业务规则里。

---

## 二、实测证据（不是纸上推测）

### 证据 1：私信"未读数"查询走不了索引

```sql
EXPLAIN SELECT COUNT(*) FROM message WHERE to_user_id = 2 AND is_read = 0;
```
结果：`type=ALL`、`key=NULL` —— **全表扫描**。

原因：索引是 `idx_from_to(from_user_id, to_user_id)`，而查未读是按 `to_user_id + is_read`，
**最左前缀用不上**。消息量一大，每次进消息中心都全表扫。

### 证据 2：同一订单可被同一个人重复评价

```sql
INSERT INTO review (order_id, product_id, from_user_id, to_user_id, star) VALUES (1,1,10,20,5);
INSERT INTO review (order_id, product_id, from_user_id, to_user_id, star) VALUES (1,1,10,20,1);
SELECT COUNT(*) FROM review WHERE order_id=1 AND from_user_id=10;   -- 结果：2
```
两条都插进去了 → 没有唯一约束拦不住。**刷好评/刷差评的入口**。

### 证据 3：同一用户对同一捡漏商品可产生多条抢购记录

```sql
INSERT INTO flash_sale_record (product_id, user_id, is_success) VALUES (1,10,1);
INSERT INTO flash_sale_record (product_id, user_id, is_success) VALUES (1,10,1);
-- 结果 COUNT = 2
```
"谁抢到了"会出现两条记录，并发场景下统计与对账直接错乱。

### 证据 4：同一交易订单可生成两个跑腿单

```sql
INSERT INTO delivery_order (trade_order_id, ...) VALUES (1, ...);   -- 两次
-- 结果 COUNT = 2
```
一对一关系没有唯一约束，重复生成跑腿单会扣两次跑腿费。

### 证据 5：捡漏专区列表查询用不上复合索引

```sql
EXPLAIN SELECT id,title FROM product
WHERE is_flash_sale=1 AND status=0 AND flash_start_time > NOW() ORDER BY flash_start_time;
```
结果：`key=idx_status`，并且 **`Using filesort`** —— 只吃到单列 `status`，
排序要靠文件排序。捡漏专区是首页入口、访问量最大，这里应该建复合索引。

### 证据 6：信用分"每日加分上限"根本算不出来

```
user 表可用于判断加分时间的字段数：0
```
需求原文（模块 1）：**"加分有每日上限，防止刷分"**。
而 user 表只有 `credit_score` 一个总分，**既没有流水也没有时间戳** →
无法知道"今天已经加了多少分"。豆包说 `credit_log` 是"可扩展、可以不做"，
但**要实现你自己写的这条规则，它就不是可选项**。

### 证据 7：管理员表不存在 → 管理后台登录会直接失败

```
employee 表数：0
```
现有工程的管理后台登录走 `/admin/employee/login` + `JwtTokenAdminInterceptor`，
依赖 `employee` 表。这份 schema 没有它。虽然 `user.role` 里写了 `2=管理员`，
但那意味着要**重写整套管理端鉴权**，否则你启动项目后连管理后台都进不去。

## 三、完整性对照（需求模块 → 字段覆盖）

| 需求模块 | 关键要求 | schema 是否支撑 | 缺口 |
|---|---|---|---|
| 1 用户 & 信用 | openid 登录 / 实名 / 信用分 / RBAC / 封禁 | 大部分 ✅ | ❌ **信用分流水缺失**（每日上限、扣分明细、投诉举证都要它）<br>⚠️ 学生证图片没字段（需求要求"上传学生证"） |
| 2 分类 | 管理员增删改 | ✅ | — |

| 4 收藏 | 收藏 / 售罄标记 | ✅ | — |
| 5 议价 | 出价≥50% / 接受·拒绝·还价 / 生成订单 / 原标价不变 | ✅ | ⚠️ 只能记录**一轮**出价（多轮还价存不下，需明确取舍）<br>⚠️ `bargain_status=5 过期` 但没有过期时间字段 |
| 6 交易订单 | 三来源 / 成交价独立 / 自提·跑腿 / 超时 / 互评 | 大部分 ✅ | ❌ **交易地点无字段**（自提订单双方无法约定在哪交接；需求明确要求"地址放到订单里"） |
| 7 跑腿 | 生成跑腿单 / 接单取货送达 / 关联主订单 / 按距离计费 / 结算 | ✅ | ⚠️ 无送达时间字段（结算统计要按时间聚合）<br>⚠️ 无计费距离快照 |

| 10 捡漏记录 | 谁参与、谁抢到 | ✅ | ❌ 无唯一约束（证据 3） |
| 11 私信 | 一对一 / **捡漏权限控制** / 敏感词 | 部分 ✅ | ❌ **无商品维度**（判不出"这两人在聊哪件商品"，权限无从校验）<br>❌ 未读查询无合适索引（证据 1） |

## 四、问题清单与修复方案

### P0 · 不补就无法实现需求（6 项）

| # | 问题 | 建议修复 |
|---|---|---|
| 1 | **无管理员表** | 二选一：① 保留 `employee` 表（管理后台代码不用改，**推荐**）② 管理员并入 `user.role=2` 并重写 `/admin/**` 鉴权 |
| 2 | **`product` 无审核状态** | 加 `audit_status tinyint`（0待审核 1通过 2驳回）+ `audit_note varchar(255)`（驳回原因，需求要求"审核驳回"）。若普通商品也审核，这个字段一表两用 |
| 3 | **`product` 无新旧程度** | 加 `condition_level tinyint`（1全新 2几乎全新 3轻微使用痕迹 4明显使用痕迹）。**别叫 `condition`**——MySQL 保留字，建表能过、查询报 1064（已实测） |
| 4 | **`trade_order` 无交易地点** | 加 `pickup_place varchar(255)`（自提地点：宿舍区/教学楼/校门口）。跑腿单的 `pick_address` 是"跑腿员去哪取"，语义不同，不是重复 |
| 5 | **`message` 无商品维度** | 二选一：① 加 `product_id` ② 新建 `conversation` 会话表（`message.conversation_id`）。推荐 ②：权限（抢购前关闭/抢到后 10 分钟窗口）是**会话级**属性，`can_send_until` 直接落在会话上 |
| 6 | **信用分无流水** | 加 `credit_log`（`user_id`, `change_score`, `reason_type`, `ref_id`(订单/投诉id), `create_time`）。它同时解决三件事：每日加分上限、扣分溯源、投诉举证 |

### P1 · 会产生脏数据（3 项，都有实测证据）

| # | 问题 | 建议修复 |
|---|---|---|
| 7 | `review` 可重复评价 | `UNIQUE KEY uk_order_from (order_id, from_user_id)` |
| 8 | `flash_sale_record` 可重复记录 | `UNIQUE KEY uk_product_user (product_id, user_id)` |
| 9 | `delivery_order` 可重复生成 | `UNIQUE KEY uk_trade_order (trade_order_id)` |

### P2 · 索引与易用性（5 项）

| # | 问题 | 建议修复 |
|---|---|---|
| 10 | 私信未读查询全表扫 | 加 `KEY idx_to_read (to_user_id, is_read)` |
| 11 | 捡漏列表 filesort | 加 `KEY idx_flash_list (is_flash_sale, status, flash_start_time)` |
| 12 | 投诉缺凭证 | 加 `images varchar(1000)`（JSON 数组，与商品多图一致） |
| 13 | 投诉类型不全 | `complaint_type` 扩展为 0商品举报 1交易纠纷 2跑腿纠纷；或另加 `complaint_reason` 细分（货不对板/虚假描述/对方失联） |
| 14 | 跑腿缺时间字段 | 加 `accept_time`、`finish_time`（接单/送达时间，结算与超时判定都要） |
| 15 | 议价"过期"无从判定 | 加 `expire_time datetime`（否则只能拿 `create_time + 24h` 硬算） |
| 16 | 订单缺取消原因 | 加 `cancel_reason varchar(255)`（原工程有，投诉举证有用） |
| 17 | 实名认证缺证件图 | 加 `student_card_img varchar(255)` |
| 18 | 默认好评无法区分 | `review` 加 `is_default tinyint default 0` |

## 五、这份 schema 做得好的地方（要保留）

1. **`openid` 替代账号密码**，且**刻意删掉了 `id_number` 身份证号** —— 敏感信息不入库，这个判断很对
2. **`address` 不放用户主表** —— 一个用户可有多个交易地点，放订单里才对
3. **成交价 `real_price` 与商品标价解耦** —— 议价/捡漏改的是订单价，商品原价保留
4. **跑腿单不冗余存买卖双方和商品** —— 通过 `trade_order_id` 拿，减少冗余
5. **捡漏不单独建表**，用 `is_flash_sale` + `flash_start_time` 标记 —— 避免表膨胀
6. **完全没有支付相关表** —— 与"平台不介入资金"的定位一致
7. 规范层面：无物理外键、金额 decimal、状态 tinyint、双审计字段、注释齐全、utf8mb4_unicode_ci 显式指定

## 六、面试追问预判（针对这份 schema 最可能被问的）

| 面试官会问 | 你要能答 |
|---|---|
| `message` 表就两个人 id，你怎么实现"捡漏抢购前关闭私信"？ | ⚠️ **当前设计答不上来**——必须补商品维度（P0-5） |
| 信用分怎么保证不被刷？ | ⚠️ **当前设计答不上来**——需要流水表（P0-6） |
| 评价能不能重复提交？ | 补了唯一索引后答："数据库唯一索引兜底 + 业务层先查再给友好提示" |
| 捡漏专区首页列表怎么保证快？ | 复合索引 `(is_flash_sale, status, flash_start_time)`，避免 filesort |
| 为什么不用物理外键？ | 性能与运维：外键在高并发写入下加锁、DDL 变更困难；关联关系由代码维护 + 应用层校验 |
| 为什么金额用 decimal 不用 float？ | float 二进制浮点有精度丢失，`0.1+0.2 != 0.3`；decimal 精确到分 |

## 七、总评与建议

**豆包这份 schema 的定位是"实体清单的物理化"**——它按 11 个名词推表，规范层面做得扎实，
所以"能跑、不难看"；但它**没有回头逐条对照你自己写的 11 个业务模块**，
于是业务规则里那些"需要一个字段才能落地"的地方全漏了（审核状态、新旧程度、交易地点、私信维度、信用流水）。

**这正是你该学到的评审方法**：
> 建表不能只看"有哪些名词"，要拿**需求文档逐条过一遍**：每条规则问一句"要落哪个字段才能实现？"
> 答不上来的，就是缺字段。

**行动建议**：先补 P0 的 6 项（其中"管理员表"和"私信会话表"是**结构性决定**，会影响后面所有代码），
再补 P1 的 3 个唯一索引，P2 可以边做边加。
