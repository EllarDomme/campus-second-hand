## 一、全局规范（写之前先记住）

| 规范 | 要求 |
|---|---|
| 引擎 / 字符集 | `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci` |
| **排序规则必须显式写** | 只写 `CHARSET=utf8mb4` 时，MySQL 8 会默认成 `utf8mb4_0900_ai_ci`（**已实测确认**），与规格要求不一致，影响排序与比较行为 |
| **字段名避开保留字** | 保留字**能建表成功，但查询时不加反引号会报 `ERROR 1064`**（已实测：`condition` 列）。完整清单见 `tools/mysql-reserved-words.txt`（262 个，取自本机 `information_schema.KEYWORDS`） |
| 主键 | 每表 `id bigint NOT NULL AUTO_INCREMENT`，关联 ID 一律 `bigint`，**禁止 varchar 存 ID** |
| 审计字段 | 每表必须有 `create_time`、`update_time`，`DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP` |
| 金额 | `decimal(10,2)`，**禁止 float/double** |
| 状态 / 角色 / 类型 | 一律 `tinyint` + 数字编码，注释里写清含义，**不存中文字符串** |
| 短文本 / 长文本 | 短文本 `varchar(n)`，大段描述用 `text` |
| 多图 | `varchar(1000)` 存 JSON 数组，**不做多列、不用单张 image** |
| 外键 | **不建物理外键**，关联关系由代码维护；关联字段建普通索引 |
| 表名 | 全小写 + 下划线 |
| 注释 | 表注释 + 字段注释都要写 |

## 二、11 张表字段规格

### 1. `user` 用户表
`id` / `openid` varchar(50) 微信唯一标识 / `nickname` varchar(55) / `avatar` varchar(255) /
`real_name` varchar(55) / `phone` varchar(11) / `student_no` varchar(20) 学号实名 /
`credit_score` int default 100 / `role` tinyint（0普通 1跑腿员 2管理员）/ `status` tinyint（0正常 1封禁）/ 审计字段

> 刻意**不要**：account、password（小程序用 openid）、身份证号（敏感，存学号即可）、address（不属于用户基础信息）、独立的信用分表。

### 2. `category` 分类表
`id` / `category_name` varchar(55) / 审计字段

### 3. `product` 商品表
`id` / `seller_id` bigint / `category_id` bigint / `title` varchar(100) / `price` decimal(10,2) /
`images` varchar(1000) JSON / `description` text / `is_flash_sale` tinyint（0普通 1捡漏）/
`flash_start_time` datetime（普通商品为 null）/ `status` tinyint（0在售 1交易中 2已售罄 3下架）/ 审计字段

### 4. `favorite` 收藏表（多对多中间表）
`id` / `user_id` bigint / `product_id` bigint / 审计字段 → **联合唯一索引 `(user_id, product_id)` 防重复收藏**

### 5. `bargain` 议价表
`id` / `seller_id` / `buyer_id` / `product_id` / `buyer_offer` decimal(10,2) /
`seller_counter_offer` decimal(10,2) null 卖家还价 / `bargain_status` tinyint（0待处理 1买家出价 2卖家还价 3接受 4拒绝 5过期）/
`order_id` bigint null 议价成功生成的订单 / 审计字段

### 6. `trade_order` 交易订单表
`id` / `order_no` varchar(32) 业务单号（对外用，**唯一索引**）/ `seller_id` / `buyer_id` / `product_id` /
`real_price` decimal(10,2) 实际成交价（与商品标价解耦）/ `deal_type` tinyint（0自提 1跑腿）/
`order_source` tinyint（1普通下单 2议价生成 3捡漏抢购）/ `status` tinyint（0待确认 1待交易 2已完成 3已取消 4超时取消）/
`expire_time` datetime 超时截止 / `finish_time` datetime / 审计字段

### 7. `delivery_order` 跑腿订单表
`id` / `trade_order_id` bigint 关联主订单 / `runner_user_id` bigint null / `pick_address` varchar(255) /
`receive_address` varchar(255) / `delivery_fee` decimal(10,2) / `status` tinyint（0待接单 1已接单 2取货中 3已送达 4已取消）/ 审计字段

> 刻意**不要**冗余存 seller_id / buyer_id / product_id——通过 `trade_order_id` 就能拿到。

### 8. `review` 评价表
`id` / `order_id` / `product_id` / `from_user_id` 评价人 / `to_user_id` 被评价人 / `star` tinyint(1~5) /
`content` varchar(500) / 审计字段

### 9. `complaint` 投诉工单表
`id` / `product_id` / `order_id` bigint null（商品举报可为 null）/ `complainant_user_id` / `respondent_user_id` /
`complaint_type` tinyint（0商品举报 1交易纠纷）/ `content` text / `handle_status` tinyint（0待处理 1处理中 2已完结）/
`handle_note` varchar(500) 管理员处理备注 / 审计字段

### 10. `flash_sale_record` 捡漏抢购记录表
`id` / `product_id` / `user_id` / `is_success` tinyint（0未抢到 1抢到）/ 审计字段

### 11. `message` 私信消息表
`id` / `from_user_id` / `to_user_id` / `content` varchar(1000) / `msg_type` tinyint（0普通文本 1系统提示）/
`is_read` tinyint / 审计字段

> WebSocket（全双工）是通信技术、属代码层，**不进数据库**；message 表只做消息持久化。

## 三、⚠️ 设计缺口：4 个需要你拍板的地方

这些需求在 docx 里讨论过，但**评审出来的字段清单没有覆盖**。别直接抄规格，先自己判断：

| # | 缺口 | 相关需求原文 | 你要决定什么 |
|---|---|---|---|
| 1 | **商品新旧程度没有字段** | 模块 3.1：卖家自主发布「标题、描述、**新旧程度**、价格、图片、分类」 | 加什么字段？用什么类型？取值怎么编码？<br>⚠️ **千万别叫 `condition`** —— 它是 MySQL 8 保留字，建表能成功但查询报 1064。建议 `condition_level tinyint`（1全新 2几乎全新 3轻微使用痕迹 4明显使用痕迹） |
| 2 | **捡漏商品的审核状态没有字段** | 模块 3.2：捡漏商品「提交后管理员审核，**审核通过才上架**捡漏专区」 | 普通商品要不要审核？audit 状态放 product 还是单独表？驳回原因存哪？ |
| 3 | **交易地点没有落表** | 第七步映射：「AddressBook（地址簿）→ 改成**交易地点**（宿舍区/教学楼/校门口）」；且要求「address 不要放用户主表，可以放到订单/跑腿订单里」 | 自提订单的地点写在 trade_order 的哪个字段？跑腿单已有取货/收货地址，会不会重复？ |
| 4 | **私信会话缺少商品维度** | 模块 11：「捡漏商品有特殊私信权限控制（预热期关闭，抢购后**仅成功者可沟通**）」 | 判定「谁能给谁发消息」时，怎么知道这条会话是针对哪件商品？message 表加 product_id，还是另建会话表 `conversation`？ |

> 第 4 个是四个里最关键的：**权限校验必须有业务上下文**，只有 from/to 两个人是判不出来的。
> 这一条你在面试里被追问「私信权限怎么实现的」，能不能答上来就看这里。

另外两个**可选**项（做了加分，不做不影响）：
- `credit_log` 信用变更流水表（记录每次加减分原因）——豆包说实习项目可不做
- 跑腿费按距离计费，是否需要存 `distance` / 计费快照

## 五、评审清单（我按这个逐条打分）

- [ ] 11 张表齐全，表名与规格一致
- [ ] 每表：bigint 主键 + create_time + update_time
- [ ] 所有关联 ID 都是 bigint，没有 varchar 存 ID
- [ ] 金额全是 decimal(10,2)，没有 float/double
- [ ] 状态/角色/类型全是 tinyint，且注释写明每档含义
- [ ] 长文本用 text，多图用 varchar(1000)
- [ ] favorite 有 `(user_id, product_id)` 联合唯一索引
- [ ] trade_order 的 order_no 有唯一索引
- [ ] 关联查询字段（seller_id / buyer_id / category_id / product_id / order_id / trade_order_id 等）都有普通索引
- [ ] 没有物理外键
- [ ] 引擎/字符集/排序规则正确，表注释+字段注释齐全
- [ ] 4 个设计缺口都给出了你的处理方案（可以不完美，但要有理由）

## 六、自检工具（写完先自己跑一遍）

我写了个静态检查器 `tools/check-schema.py`，不连数据库，随时可跑：

```powershell
cd E:\DeskTop\campus-second-hand
& "C:\Users\34684\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe" tools/check-schema.py sql/schema.sql
# 只检查部分表时：
#   ... tools/check-schema.py sql/schema.sql --expect user,product,trade_order
```

它会检查：表是否齐全、id 主键与类型、审计字段、关联 ID 是否 bigint、金额是否 decimal(10,2)、
状态字段是否 tinyint、长文本是否 text、引擎/字符集/**COLLATE 是否显式**、物理外键、表/字段注释、
关联字段索引、**字段名是否为 MySQL 保留字**、favorite 联合唯一索引、trade_order.order_no 唯一索引。

- `ERROR` = 必须修复（退出码 1）
- `WARN` = 建议确认，可能是有意为之
- 它只做文本分析，**不能替代人工评审**（比如状态枚举是否合理、索引是否命中真实查询，仍要我看）

**自检通过 ≠ 直接交付**，但能让你把低级错误自己挡掉，评审时我们只讨论设计问题。
